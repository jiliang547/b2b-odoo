# ERP 订单临时故障重试修复

## 原因与处理

S00004 在准备订单数据时遇到网络故障，原实现将全部 UserError 当作不可重试的业务错误，一次失败便进入 dead 状态。

- 为网络故障、超时及 HTTP 408/429/500/502/503/504 增加可重试异常类型。
- 复用现有 ERP 集成任务的退避间隔、次数上限和人工重试入口，不建立第二套队列。
- 配置、授权和业务校验错误停止自动重试，交由运营处理。
- 错误包含准备/发送核验阶段及接口路径，不记录访问令牌、查询参数或请求正文。
- 保持冻结请求、原订单编号、防重键和发送前查询机制；不在 HTTP 层自动重发新增请求。

## 进一步防重（19.0.1.2.1）

- 新增请求发出前独立持久化提交记录；即使当前业务事务回滚或服务退出，该记录仍存在。不提交当前订单事务。
- 同一个防重键只允许一次新增尝试。之后自动或手动重试都只查询；查询暂时为空也不再新增。
- 保存明确的 ERP 返回 ID，优先按 ID 核验；缺少 ID 则使用原 ERP 单号查询。
- 查询已发现 ERP 单据时，也立即进入只核验模式，防止后续详情超时、数据不一致或列表暂时查不到导致再次新增。
- 状态显示 Submitted / Outcome Pending Verification；任务按钮显示 Recheck ERP Result，并提示不可重新创建。
- 超过重试上限、明确业务拒绝或数据不一致时人工介入；不提供一键清除防重记录。极端情况下，提交记录已保存但网络请求尚未发出便崩溃，也需要人工核对。这里优先保证不重复下单，而非自动重发一切失败请求。
- 升级前已生成请求的旧任务保守地进入只核验模式，不假设旧任务从未发送。确认不存在但又被保护拦截的历史任务需要人工核对处理。
- 独立记录只保存内部随机键和 ERP ID，不保存密钥、正文或客户资料；后台沿用现有集成任务队列、权限和重试机制。

本轮以模拟响应测试“响应丢失”和“ERP 列表延迟可见”，不向真实 ERP 重复发起新增请求来验证防重键。应用自身已阻止第二次新增，不依赖尚未充分实测的 ERP 幂等保证。
