# 付款通知取消自动订单PDF附件

网站模块版本：19.0.1.16.26。

## 调整范围

复用原生 `mail.template.write`，在安装和升级时从以下模板移除 `sale.action_report_saleorder` 自动报表附件：

- Sales: Order Confirmation（订单确认）
- Sales: Payment Done（付款通知）

不删除邮件模板，不覆盖正文、收件人、翻译或静态附件；仍使用原生邮件通知和订单访问机制。不更改付款状态、金额、订单确认条件或ERP传单规则。

手工发送报价单、原生Proforma、Payments & PI中的 Download Current PI 保持不变。今后不要给以上两个支付通知模板重新添加动态PDF报表；否则仍可能在付款后处理期间触发PDF生成。其他自定义动态附件不在本次删除范围。

## 验证

收款模块50项模型回归全部通过，日志 `payment-no-pdf-final-tests.log`。新增覆盖：两类通知生成不调用PDF渲染；原生报价及Proforma仍保留报告；银行部分到账再在线补足30%定金，模拟PDF渲染不可用时仍完成原生交易后处理与订单确认。

首次测试新增用例误用了不存在的测试付款条件XML ID，改为现有 b30 后完整重跑50项通过，没有为通过测试修改业务确认条件。

本地原订单 S00002 在本次配置更新前已由后台重试恢复（2026-09-24 15:31左右），不是本次手工改成成功：银行25、Demo 1.73、合计26.73，剩余62.37。没有新建交易或重复支付。此次调整用于去掉重复发生该问题的自动附件生成步骤。

PDF程序版本为0.12.6 with patched qt，历史退出错误并非持续不可用；取消邮件附件不等于修复PDF工具本身，主动下载功能需单独验证。

本地更新另发现旧出口语言清理代码在存在中文订单行、但zh_CN未启用时使用无效语言上下文，导致升级失败。已仅增加启用状态判断：不启用语言、不猜测翻译、不修改此类订单行；新增独立回归验证。

该补充测试1项通过，合计分两次验证51项。最终本地升级成功，两类通知 report_template_ids 均为空，手工报价模板仍保留报表。浏览器以管理员的客户预览模式查看S00002，显示 Order Confirmed、Deposit Received；实际点击 Download Current PI，新PI成功生成并返回HTTP 200（15:39:03，首次请求约56秒）。这验证下载入口与实际生成，未宣称完成PDF视觉排版验收或解决Windows渲染慢的原因。

未向S00002追加尾款或新交易；未修改ERP客户/订单；未推送GitHub。PDF慢和历史异常退出的底层原因尚未定论，本次已去掉其与支付通知的直接依赖。
