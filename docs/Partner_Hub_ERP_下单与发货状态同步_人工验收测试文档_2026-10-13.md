# Partner Hub ERP 下单与发货状态同步人工验收测试文档

版本日期：2026-10-13。测试状态：待执行。

本轮验收两条业务链：客户在网站下单，符合现有付款或信用条件后生成正式订单，并在用友 C4 创建一张对应销售订单；ERP 人员随后处理供应、入库、分批出库，客户在网站 Order Progress 页面查询每个商品的进度。

必须通过实际页面点击执行客户、运营和财务操作。直接调用模型确认订单、修改数据库状态或伪造成功回调，不能替代人工交互验收。后台日志、只读接口查询和报表导出可以辅助核对结果。

本文件是执行计划，不是测试通过报告。以前的接口测试和自动化回归结果不能填写为本轮实测结果。

## 1 验收范围与当前边界

### 1.1 本轮必须验证的业务结果

1. 客户加购、结账、提交订单和付款入口可实际使用，不跳到原生错误页面。
2. 未确认的报价单不被提前传入 ERP；正式订单确认后能够排队、创建、查回并显示 ERP 单号。
3. ERP 中客户、业务员、部门、组织、商品、数量、币种、单价、税额、运费和合计与网站最终订单一致。
4. 同一正式订单只有一个 ERP 销售订单，付款尾款、页面刷新和异常重试不产生重复订单。
5. 多商品订单按商品分别展示供应订单下单日期、最终约定完工日期、入库日期、销售出库日期和已发数量。
6. 部分发货、后续补发、手动刷新和查询失败时，客户不会看到错误的数量、他人订单或被清空的历史进度。

### 1.2 当前功能边界

| 项目 | 本轮处理方式 |
| --- | --- |
| ERP 写入组织 | 全部限定用友测试组织 `999`，不得改为正式组织 |
| ERP 创建触发 | Odoo 报价单真正成为正式销售订单时触发，不是单纯点击 Submit Order、上传付款截图或生成 PI 时触发 |
| ERP 审核、供应、入库、出库 | ERP 人员按现有 ERP 流程处理，网站不会替 ERP 自动审核或发货 |
| 状态来源 | 全流程报表 `xinquanliucbiao`，不是快递公司的实时物流轨迹 |
| 财务接口 | 不验收 ERP 收款、记账、开票等接口；网站付款只是验证订单确认条件 |
| 旧订单 | 不自动补传。优先用本轮新订单，不拿历史订单直接点重复确认来测试新增 |
| ERP 改单、取消 | 尚不自动执行。本轮只检查人工核对标记和防重复创建保护 |
| Odoo 库存与工厂 | 不在 Odoo 伪造入库、出库或工厂生产来证明 ERP 同步；本轮履约来源是外部 ERP |

**多行报表是重点限制：** 当前实现会按 ERP 销售订单子表 ID 区分商品，但同一销售订单行出现多条报表记录时，不直接求和或取最大值来认定累计已发数量。日期可展示，数量可能显示 `Shipment quantity pending`。这能避免重复累计，但不等于已经满足“客户能准确看到分批累计已发数量”的业务目标。相关用例必须分别记录数据安全结果和业务完成结果。

## 3 测试前检查

### 3.1 连接与后台任务

管理员打开 **B2B Management → Configuration → Yonyou ERP Mapping**：

1. 确认 **Restrict All Organizations to 999** 已勾选。
2. Management Org、Default Use Org、**ERP Sales / Invoice / Stock Organization** 均为 `999`。
3. **Enable Mapping Queries** 已开启；用于客户、商品和进度查询。
4. **Send Newly Confirmed Orders to ERP** 已开启；它和注册审核同步客户的开关是两件事。
5. **USD to CNY Interface Rate** 核对为本轮约定值，例如 `6.30000000`，不要在订单发送途中更改连接身份或汇率。
6. App Key、App Secret 已在当前环境配置，相关接口已授权。不在测试文档、客户页面或截图中记录密钥和 access token。
7. 当前业务接口网关为 `https://c4.yonyoucloud.com/iuap-api-gateway`。

在原生计划任务中核对以下任务启用且有执行记录：

| 计划任务名称 | 当前模块默认规则 |
| --- | --- |
| B2B: Process ERP Integration Jobs | 默认每 5 分钟检查；新确认订单和准备完成时会主动触发任务 |
| Partner Hub: Requested Order Progress | 默认每 1 分钟处理已请求刷新的订单，不扫描所有订单向 ERP 全量查询 |

升级前已经人工调整的任务可能保留原有间隔，执行记录应填写实际值。若后台任务停用，先处理配置，不把长期 Pending 直接认定为接口下单失败。

### 3.2 客户与价格

运营打开 **B2B Management → Business Data → Customers**，进入客户甲所属的公司档案，打开 **Partner Hub**：

1. 审批状态正常，Account Brand 和 Assigned Selling Company 正确。
2. ERP Customer Code 填入已存在、可在组织 `999` 使用的客户编码。
3. 点击该编码旁的 **Verify & Refresh**，检查映射为 Verified，并带出 ERP 客户名称、默认业务员、部门和 ERP Order Currency。
4. 客户分类旁的 **Verify** 只验证分类，不代替客户验证。不要把分类编码当成客户编码。
5. 网站价格表币种与 ERP Order Currency 一致。ERP 交易币种未维护时当前接口使用 USD；不自动把已付款订单换成另一币种。
6. 基础价格和公司专属价格已配置，客户能看到最终价格并加购。
7. 客户国家信息和原生税规则一致。本项目接口约定：中国大陆客户为不含税价加 13%，其他国家或地区为 0% 或原生无税。

需要测试 20% 定金时，使用已配置相应付款条件的专用测试客户。不要为了执行用例，反复更改真实客户或共享付款模板。

### 3.3 商品与运费

1. 准备两个不同实物商品 A、B，两者具有不同且真实存在的 ERP 物料编码。
2. 后台商品资料打开 **Partner Hub → ERP Material Mapping**，点击 **Verify**；多变体到各变体的 **ERP Mapping** 分别验证。
3. 检查一个 Odoo 基础单位与一个 ERP 基础单位表示相同数量；修改单位后重新验证。
4. 确认商品对客户可见、价格有效、MOQ 允许本轮数量、销售税适用正确。
5. 默认人工运费模式下订单不应自动增加零元配送行。收费时使用网站配置的 Freight Product；该服务商品也必须有真实且已验证的 ERP 运费料号。

测试计划：

| 明细 | 下单数量 | 第一次发货 | 第二次发货 | 最终累计 |
| --- | --- | --- | --- | --- |
| 实物商品 A | 10 个基础单位 | 4 | 6 | 10 |
| 实物商品 B | 20 个基础单位 | 0 | 20 | 20 |
| 运费服务商品 | 需要时为 1 | 不适用 | 不适用 | 不应被当成待发实物 |

A 可选历史已验证过的物料 `000020`，本轮仍需核验。B 必须由 ERP 人员提供另一真实物料，不能随意编造编码。数量不符合 MOQ 时，调整为符合条件的数值，并同步修改分批发货计划。

价格以客户实际看到的价格为准。举例：A 单价 100 USD、B 单价 50 USD、无税无运费时，总额为 2,000 USD，20% 定金为 400 USD。该例用于算账核对，不要求覆盖现有价格表。

### 3.4 银行付款测试准备

只使用本地或明确的测试数据库进行模拟到账，不发生真实转账，不把普通商品图片当成真实银行付款证明。

财务提前检查对应销售公司的银行日记账、币种、银行账户持有人、客户应收科目和 Manual Payment 收款方式的未结清收款科目。只配置了银行账户名称，不代表原生收款可以过账。

凭证测试可选择 `D:/Desktop/ScreenShot_2026-09-09_113752_318.png`，并把提交备注标为测试图片，不代表真实到账。

### 3.5 ERP 履约准备

ERP 人员确认测试组织中有可使用的库存组织、仓库和供应流程。所有测试供应、入库、出库单据须限定在获准测试范围内；库存不足时不得借用正式组织的库存来完成测试。

先确认全流程报表包含本轮销售订单，能用其 **源头单据号** 查出明细。ERP 的报表生成、刷新或统计生效延迟也要记录，网站不能展示接口尚未返回的新数据。

## 4 常用入口与等待规则

| 要做什么 | 实际入口或按钮 |
| --- | --- |
| 客户提交待调整订单 | 商品详情 Add to Cart → 购物车 Checkout → 确认地址 → Payment → More options → Submit Order |
| 客户在线付款 | Payment → More options → Pay now；已发布报价也可从订单详情 Review & Pay 进入 |
| 客户银行付款 | Payment → Pay by Bank (TT) → Payments & PI → Pay by Bank Transfer → Submit Payment Proof |
| 运营调整报价 | Sales → Orders → Quotations，按网站单号打开；Order Lines 添加或修改明细，保存后点 Release for Customer Payment |
| 财务审核凭证 | B2B Management → Operations → Bank Transfer Reviews，按订单号找本次凭证 |
| 核对 ERP 下单结果 | 后台销售订单 Other Info：ERP Submission、ERP Order Number、ERP Order ID |
| 检查该订单任务 | 后台订单顶部 ERP Jobs；也可用 B2B Management → Operations → ERP Jobs |
| 客户查进度 | My Account → Orders & Payments → 对应订单 → Order Progress；地址形如 `/my/orders/订单内部ID/erp-status` |
| 客户主动查新进度 | Order Progress → Refresh Progress |
| 后台查新进度 | 订单 Other Info → Refresh Order Progress，需集成管理员权限 |

网站单号例如 `S000xx`，ERP 单号通常为 `PH-T-年份-序号-后缀`。到 ERP 查询时，复制后台 **ERP Order Number**，不要只拿网站单号搜索。

### 4.1 订单提交与回查

任务先准备并保存固定请求，之后才调用新增接口。第一次点击 Process Now 可能只完成准备；重新打开同一任务核对状态，必要时再处理下一阶段，不要复制任务。

| 状态 | 含义和测试处理 |
| --- | --- |
| Pending / Processing | 正在准备或发送，等待后台执行；不能据此判断 ERP 已有或没有订单 |
| Created in ERP | 已查回并核对数据；仍需 ERP 人员实际打开单据比对 |
| Submitted / Outcome Pending Verification | 已尝试发送或已发现 ERP 单据，结果待核验；不是“未下单” |
| Retry / Verification Required | 查看同一任务的 Last Error、Next Retry At，不复制订单 |
| Action Required | 需要人工检查；不清除防重记录、不生成替代 ERP 单据 |

默认临时故障退避按尝试次数为 5、10、20、40 分钟继续递增，通常达到默认 5 次尝试上限后转人工处理；准备阶段也计入次数，所以不能只按“网络失败了几次”推算。实际以 **Attempt Count / Next Retry At** 为准。人工重试会把同一任务重新排回 Pending，不清零已经累计的尝试次数，也不会解除新增防重保护；已达上限的任务再次失败时可能直接回到人工处理状态。

已经尝试新增后，**Recheck ERP Result** 或自动重试只回查，不再次新增。重新查询还没查到也不允许盲目重发。

### 4.2 订单进度刷新

| 情况 | 当前行为 |
| --- | --- |
| 首次进入可查询的订单进度页 | 请求后台查询，页面等待结果；不是在浏览器里直接访问 ERP |
| 最近已成功查询 | 缓存有效期为 30 分钟，重新进入通常显示缓存 |
| ERP 刚更新，希望立即查看 | 使用 Refresh Progress，可绕过成功缓存，但有约 60 秒订单级冷却 |
| 多联系人、多个标签页连续点击 | 同一订单合并刷新请求，冷却共享，不能无限触发 ERP 查询 |
| 已在刷新 | 按钮为 Refreshing…，等待期间约每 3 秒查询网站本地结果，不是每 3 秒请求 ERP |
| 页面等待超过约 90 秒 | 停止本轮前端轮询并给出提示；后台可能仍继续，不代表 ERP 没有数据 |
| ERP 临时不可用 | 保留上次成功结果，暂缓约 5 分钟；手动按钮不绕过失败退避 |
| 字段、数量、行身份等数据异常 | 保留历史结果并要求核对，当前约 30 分钟退避 |

以上是当前模块规则，不是外部 ERP 的响应时限承诺。日期来自报表；Last successful update 使用 UTC，应与本地执行时间分开记录。

## 5 网站下单与 ERP 创建验收

以下用例默认状态均为未执行。先完成 T01 至 T07，再进入履约主流程。

### T01 提交待调整订单不提前创建 ERP 单

**操作人：客户、运营、ERP 人员。**

1. 客户登录，分别打开 A、B 商品详情，设置数量 10、20，实际点击 Add to Cart。
2. 打开购物车，核对商品、数量、价格、税额；默认没有 Standard delivery 零元运费行。
3. 点 Checkout，核对并选择实际收货地址、账单地址，点 Confirm 到 Payment。
4. 展开 More options，点击 Submit Order，记录生成的网站单号。
5. 客户详情应显示 Awaiting Final Quote；运营按单号打开报价，检查状态未成为正式订单。
6. ERP 人员确认没有因本次未确认报价新增销售订单；后台也不应出现本次用友新增任务。

**通过标准：** 按钮可点击，页面正确跳转，报价保留 A、B 明细，不提前传单，没有原生错误页面。

### T02 最终报价与人工运费

**操作人：运营、客户。使用 T01 的报价。**

1. 运营核对最终商品和数量；需要收取运费时，在 Order Lines 添加已配置的运费服务商品，数量 1，单价填写约定值。
2. 保存。客户可见描述建议填写 `Freight`，不修改真实 ERP 物料名称。
3. 点击报价上的 **Release for Customer Payment**，发布最终金额。Ready for Payment 是客户看到的状态，不是后台按钮名称。
4. 客户刷新订单详情，核对 Ready for Payment、运费行、总额和应付定金金额；未加运费时不应凭空出现配送行。
5. 此时尚未符合付款或信用确认条件的报价仍不应传 ERP。

**通过标准：** 人工运费只加一次，不被刷新改回 0；FOB / EXW 商品金额门槛不包含运费；客户看到的最终明细和后台一致。

### T03 Demo 成功付款后创建一张 ERP 销售订单

**操作人：客户、运营、集成管理员、ERP 人员。使用 T02 的报价。**

1. 客户点击 Review & Pay，打开原生 Pay Order 窗口，核对 Full amount / Down payment。
2. 选择 Demo 测试支付，按其测试界面输入示例数据，Payment Status 选择 Successful，不勾选保存支付资料，点击 Pay。
3. 确认支付结果和订单列表更新；达到该客户确认条件后，后台应成为正式销售订单。若付款条件需要 100%，不足金额不能被当作已确认。
4. 集成管理员打开该单 ERP Jobs，观察准备、发送和查回；无异常时等待自动处理。需要加速时只在原任务上使用 Process Now。
5. 后台 ERP Submission 应最终显示 Created in ERP，并有 ERP Order Number、ERP Order ID。
6. ERP 人员按 ERP Order Number 打开唯一销售订单，逐项完成第 6 节对照。

**通过标准：** 网站付款不被重复收取；只生成一张 ERP 单；不是仅凭网站成功提示或接口返回码就宣布通过。

### T04 银行凭证上传不等于订单确认

**操作人：客户、财务、ERP 人员。新建一张 20% 定金条款的 A、B 测试订单。**

1. 客户在 Payment 点击 Pay by Bank (TT)，进入 Payments & PI。
2. 检查订单总额、20% Due Now、品牌收款信息，以及 Pay by Bank Transfer 上传入口。
3. 填写测试转账金额、日期、参考号，选择测试图片，备注“测试图片，模拟到账”，点击 Submit Payment Proof。
4. 财务从 Bank Transfer Reviews 找到本次凭证；先不确认实际到账。
5. 客户应能看到凭证待审核，但已确认收款不能增加；订单仍不得仅凭图片就触发 ERP 新增。

**通过标准：** 凭证归属正确、入口可用，上传图片不被误当成真实付款或正式订单。

### T05 不足定金与达到定金阈值

**操作人：财务、客户、集成管理员、ERP 人员。继续 T04。**

1. 财务打开该凭证，点击 Register / Open Receipt。
2. 在原生银行收款表单核对买方客户、销售公司、银行日记账、币种、收款方向和金额。先登记低于应付定金的测试实际到账，例如总额的 10%。
3. 保存并按原生流程确认或过账；确认对应分录为 Posted。返回该凭证，核对关联的 Native Bank Receipt 和 Allocated Amount，然后点击 Confirm Actual Receipt。
4. 客户检查已收金额增加，但 20% 阈值尚未达到；不应创建 ERP 正式单。
5. 客户再上传第二笔模拟凭证；财务使用新的原生收款记录，登记另外 10%，分别确认实际到账。
6. 达到 20% 后检查原订单变为正式订单、ERP 任务入队，并在 ERP 找到唯一对应订单。
7. 比较 ERP 总金额和明细：应传整单全部商品、数量、运费及总金额，不是只传 20% 的金额或商品数量。

**通过标准：** 不足阈值不提前传单；达到阈值只传一张整单；不重复使用同一收款流水计算两次到账。

若提示缺少科目、未结清收款账户或公司不一致，先记录为会计配置问题并处理，不通过直接改收款状态来继续测试。

### T06 尾款不重复下单

**操作人：客户、财务、ERP 人员。继续 T05。**

1. 客户在 Payments & PI 继续走银行转账，上传剩余款项的测试凭证。
2. 财务登记、过账并确认本次收款，核对累计已收和余额。
3. 刷新客户订单、后台 ERP Jobs 和 ERP 查询结果。
4. 记录尾款前后的 ERP Order Number、ERP Order ID 和 ERP 销售订单数量。

**通过标准：** 累计收款正确、余额正确；ERP 单号和 ID 不变，仍只有一张订单，没有第二次新增。若另测混合在线尾款，使用测试支付提供商，单独记录结果。

### T07 无运费与有运费两种订单

**操作人：客户、运营、ERP 人员。**

1. 对比 T03 的人工运费订单和 T05 的无运费订单；若前者未添加运费，另建一张明确添加运费的测试报价再走确认流程。
2. 无运费：网站与 ERP 均不得出现系统自动加上的零元配送明细。
3. 有运费：网站有一个约定金额的服务明细，ERP 有一个对应运费料号，数量 1、税额和金额正确。
4. 运费不另加到独立字段造成重复收费；客户 Order Progress 不应把它显示为待发实物。

**通过标准：** 运费完全按运营最终报价传输，服务行显示 No shipment required。

### T08 不同币种税率及单位

**操作人：运营、客户、ERP 人员。扩展测试使用专用客户和新订单。**

| 子场景 | 核对点 |
| --- | --- |
| ERP 交易币种未维护 | Verify & Refresh 后订单使用 USD，接口汇率为本轮配置值；不取注册资金币种 |
| ERP 交易币种为 CNY | 网站报价 CNY，原币 CNY、本币 CNY、汇率 1 |
| 中国大陆客户 | 商品价格仍为未税价；结算计算 13%，ERP 明细和总税额一致 |
| 非中国大陆客户 | 原生 0% 或无税，ERP 税率 0%；不能再次加 13% |
| Odoo 订单使用非基础单位 | 按实际单位关系核对 ERP 基础数量；进度中的已发及剩余数量使用商品基础单位，不能直接与“箱数”等订单单位比较 |
| 不同 Odoo 销售公司 | 单据销售主体、日记账和税属于客户绑定的销售公司；接口测试组织仍为 999，不依赖操作员当前公司猜测 |

**通过标准：** 不修改已付款订单的币种或金额来迎合 ERP。没有合适安全测试资料的子场景标记未执行，不能视作通过。

### T09 待处理或失败支付

**操作人：客户、运营。单独新建测试报价。**

1. Demo 选择 Pending，点击支付，核对待处理提示和重复支付保护。
2. 在尚未达到该单确认条件时，不得出现正式 ERP 订单。
3. 另建一张测试报价使用 Cancelled 或 Error，验证错误留在网站设计的页面或提示中，原订单不被误确认。

**通过标准：** 待处理、失败和成功不混淆，不靠重复创建付款或复制订单推进流程。

### T10 缺失映射或币种税率不一致

**操作人：运营、客户、集成管理员。仅使用专用测试资料。**

1. 使用未验证物料的测试商品，或故意未完成客户映射，尝试结账、发布报价或检查 ERP 设置。
2. 核对用户提示、后台错误归因和是否已有付款；错误不能静默吞掉或产生错误的 ERP 单据。
3. 恢复正确配置，重新 Verify，再按提示从原有流程继续。
4. 不修改真实商品或真实客户映射来制造故障；不能清空已提交订单的防重标记。

**通过标准：** 配置不完整时阻止错误业务传输；错误有清楚归因和安全恢复方法。若错误发生在已冻结订单后，先人工核对，不要求自动重写冻结请求。

### T11 ERP 已创建但网站回查失败

**操作人：集成管理员、ERP 人员。仅在获准的隔离测试环境安全模拟。**

1. 使用接口模拟或受控测试故障，在一张测试订单已被 ERP 接收后让查询阶段暂时失败。普通运营不得通过乱改真实密钥制造故障。
2. ERP 人员按原 ERP Order Number 查询，确认单据实际存在，并记下 ID。
3. 检查后台 Submitted / Outcome Pending Verification、Last Error、Next Retry At，明确失败发生于回查而非认定未新增。
4. 恢复查询；等待自动回查，或在同一任务上点击 Recheck ERP Result，按需 Process Now。
5. 再查询 ERP，确认没有新增第二个 ID；网站最终绑定原订单并显示 Created in ERP。

**通过标准：** 超时不等于未创建；所有后续操作只核验原单，不能重复新增。无法安全制造故障时本用例标记未执行，不用已有自动化通过记录代替人工实测。

## 6 每张成功 ERP 订单的字段对照

网站、Odoo 后台和 ERP 三处都应记录证据。ERP 单据中名称可能不同，按业务字段核对，不只看单号。

| 核对项 | 期望 |
| --- | --- |
| ERP 单号与 ID | 后台 ERP Order Number / ID 与 ERP 实际单据完全一致；长 ID 按文本保存，避免 Excel 科学计数和精度丢失 |
| 来源和唯一性 | 能追溯到本次网站单号；同一 ERP 单号只有一个不同的 ERP 主表 ID，列表出现多明细行不算多张订单 |
| 销售、开票、库存组织 | 本轮均为 999；开票、库存组织随接口销售组织一致 |
| 交易类型、汇率类型 | KC 库存销售、03 特美声自定义汇率 |
| 买方、开票客户 | 买方为下单客户绑定的 ERP 客户；开票客户来自其 ERP 默认开票配置，不猜测与买方必然相同 |
| 销售部门、业务员 | 客户在目标使用组织下的默认负责人和部门；不是网站登录人、付款人或审批操作员 |
| 原币、本币、汇率 | 原币按 ERP 客户交易币种，未维护默认 USD；本币 CNY；USD 使用本轮配置汇率、CNY 使用 1 |
| 单据日期、汇率日期 | 当前实现按正式确认订单时保存的日期，以北京时间日期生成，不要求等于最初加入购物车的日期 |
| 物料与变体 | 每行是对应商品或变体的 ERP 物料编码和有效单位；不以商品中文或英文名称代替绑定 |
| 数量与金额 | 明细数量、折后未税金额、税额、价税合计和整单总额一致；单价因折扣或单位换算可与原标价不同 |
| 运费 | 只在运营明确添加时传一个真实映射服务料号；不另造零元配送行、不重复收费 |
| 电源插头、工作电压 | 当前接口预填“无”对应值，ERP 人员需人工确认真实需求后调整 |
| 是否打托、销售类型 | 打托为是，普通销售 |
| 计划发货日期 | 当前接口为正式确认日期加 90 天；不是查询页中“最终约定完工日期”的替代值 |
| 收货资料和备注 | ERP 人员人工核对实际收货信息、插头、电压和客户要求；当前尚无专门的完整收货地址自动映射，不能当成已全自动闭环 |

如果 ERP 人员在首次查回完成前调整了业务员、数量或金额，网站可能因和冻结请求不一致而停止绑定。应先完成首次验收，再做 ERP 原有业务处理；必要业务调整记录为人工核对，不以再建一张单规避校验。

## 7 ERP 履约与客户查询主流程

优先使用 T05 已传成功的无运费、两商品订单作为履约主单。由 ERP 人员从实际销售订单创建关联的供应和出库业务，不直接手工篡改网站缓存或报表导出文件。

每次 ERP 操作后的核对顺序相同：ERP 单据生效 → 全流程报表对应行已更新 → 客户点击 Refresh Progress → 网站逐商品比对。仅完成第一步不能认定网站同步失败，也不能认定同步成功。

### P01 ERP 已有销售订单但暂时没有供应记录

1. 客户从订单详情点击 Order Progress，不用管理员会话替代客户会话。
2. 首次查询时观察 Updating order progress…，等待后台查询；记录 Last successful update。
3. ERP 全流程报表尚无该单供应数据时，网站应仍展示 A、B 商品和订购数量，日期为 Not available yet，未知已发数量为 `—`。
4. 若 ERP 单据还在绑定中，页面应提示正在注册履约，不泄露接口错误或密钥。

**通过标准：** 空报表不被显示成已全部发货，也不把未知数量伪造为 0；没有白屏或原生错误页。

### P02 供应订单日期与约定完工日期

**操作人：ERP 人员、客户。**

1. ERP 人员在测试组织按已有流程生成与主单 A、B 对应的供应业务，填入可区分的供应下单日期和最终约定完工日期。
2. 打开全流程报表，按主单 ERP Order Number 查找，确认源头单据主表/子表 ID、物料编码和两个日期正确。
3. 客户在冷却结束后点击 Refresh Progress，等待完成。
4. 逐商品核对 Supply Order Date 和 Expected Completion Date，检查日期没有串到另一个商品或另一个客户。

**通过标准：** 报表和网站一致；没有入库、出库时对应日期仍为空，不用“确认日加 90 天”填充实际进度。

### P03 入库日期

1. ERP 人员只对 A 完成测试入库，按 ERP 原有审批或生效流程完成，B 保持未入库。
2. 确认全流程报表的 A 入库日期已出现，B 入库日期仍空。
3. 客户刷新 Order Progress，核对 A 的 Warehouse Receipt Date 和 B 的缺失日期。

**通过标准：** 入库不等于销售出库；不能因为 A 入库就把 A 或 B 显示成 Fully shipped。

### P04 第一次分批销售出库

1. ERP 人员从该销售订单关联创建第一批出库：A 为 4，B 为 0。完成 ERP 要求的审批和生效步骤。
2. 先核对全流程报表。期望 A 的累计已发为 4、未发为 6；B 的累计已发为 0、未发为 20。必须确认字段是累计值还是每批值，以及一行对应什么业务粒度。
3. 客户点击 Refresh Progress，核对 A 的 Dispatch Date、Shipped Quantity、Remaining Quantity 和商品状态。
4. ERP 同一销售订单行只返回一条完整有效的累计数量记录时，网站 A 应为 Partially shipped、4/6；B 应为 Not shipped yet、0/20。
5. 若该行返回多条报表记录或数量未维护，按 P06 记录限制，不能把 `—` 当成实际 0 或当成“数量验收通过”。

**业务通过标准：** 客户能看到每个商品正确累计数量和状态。安全地提示待核验只能记为安全保护符合，业务目标仍待完善。

### P05 剩余数量发货与全数发货

1. ERP 人员完成第二批出库：A 再发 6，B 发 20。
2. 报表核对累计 A 已发 10、未发 0；B 已发 20、未发 0。不能把第二批的 6 错当成 A 累计数量。
3. 客户刷新，核对日期更新；可识别的累计数量应为 A 10/0、B 20/0，状态 Fully shipped。
4. 等冷却结束后再刷新一次，并重新进入页面，数量不能重复加到 A 16 或 20、B 40，日期不能反复重复堆叠。
5. 观察其他页面是否准确表达状态；当前功能主要更新 Order Progress，不承诺同步修改 Odoo 库存单、订单总状态或快递签收状态。

**通过标准：** 逐商品累计量正确、重复刷新稳定；仅显示销售出库，不编造物流签收。

### P06 同一商品多供应记录与报表重复行

**本项为商业化验收重点。**

1. ERP 人员让 A 产生两条不同供应记录或两次关联出库，使同一个源头销售订单子表 ID 在报表中出现多行。
2. 导出或只读查询这几行，记录各行的源头主表 ID、子表 ID、物料编码、供应行号、四个日期、下单数量、销售出库数量和销售未发数量。
3. ERP 人员确认这些数量是重复的整行累计值、各批数量还是其他统计口径，不能仅凭名称推断。
4. 客户刷新并展开 View supply progress details，核对各条 Supply record 的日期。
5. 检查系统没有把重复累计量相加，也没有把其中一个日期和另一个批次错误配对。
6. 分别填写下表，不合并成一个“通过”。

| 验收层面 | 当前可能出现的结果 | 如何判定 |
| --- | --- | --- |
| 数据安全 | 日期可见，数量为 Shipment quantity pending / `—` | 没有伪造数量，可判安全保护符合 |
| 客户业务目标 | 客户仍看不到准确的累计已发、剩余数量 | 待完善，不能宣布分批发货闭环全部通过 |
| 数据已具备明确累计口径 | 报表有可唯一识别的、可信的累计结果 | 核对网站是否正确采用；当前多行仍待核验时提交功能差距，不通过改数据掩盖 |

记录待完善项时，应同时附上真实报表样本和 ERP 人员解释，再决定改报表口径还是调整网站汇总规则。临时可由运营通过订单消息告知数量，但这不等于自动同步已经实现。

### P07 手动刷新与冷却

1. ERP 刚更新某个日期后，不等待 30 分钟缓存过期，客户使用 Refresh Progress。
2. 按钮应显示 Refreshing…并暂时不可重复点击；查询完成后显示 Progress updated. 或 Progress checked. No new updates.
3. 在冷却内连续点击、打开第二个标签页，不能重复堆积 ERP 查询，不能重复新增销售订单。
4. 冷却到期后按钮恢复；在没有新业务变化时再刷，数据内容稳定，成功更新时间可以更新。

**通过标准：** 可以主动查询新数据，按钮和提示不跳动、不报原生错误；并发受控。没有新数据与查询失败必须分开提示。

### P08 重新进入页面与缓存

1. 成功刷新后离开 Order Progress，立即重新进入，核对仍显示成功快照，不必须再调用 ERP。
2. 缓存到期后重新进入，观察是否产生新的请求并更新；可以实际等待 30 分钟，不能通过改数据库时间冒充人工验收。
3. 打开网站其他页面或订单消息，不应无条件查询所有订单。

**通过标准：** 按需刷新，不以固定每小时扫描全部订单的方式运行。未完成真实等待的部分标记未执行。

### P09 查询失败保留已知进度

**操作人：集成管理员、客户。仅在隔离测试环境模拟。**

1. 先取得含日期和数量的有效成功快照，记录时间与内容。
2. 模拟报表接口超时或暂时不可用，客户点 Refresh Progress。
3. 网站显示暂时延迟并保留旧日期和数量，不归零、不清空、不假装刷新成功。
4. 后台 Other Info 记录 Progress Update Error、Last Progress Attempt；Last Successful Progress Update 不能被失败时间覆盖。
5. 不绕过失败退避，恢复后按规则再查询。确认只调用查询，不重新创建 ERP 订单。

**通过标准：** 失败明确可见，历史数据保留，恢复后继续使用原订单。

### P10 客户与公司隔离

1. 客户甲可打开自己的主单 Order Progress 并刷新。
2. 客户乙属于不同客户公司，使用甲的同一进度页地址，应无权查看；页面不能出现甲的商品、日期、数量或订单信息。
3. 未登录会话访问同一页，要求登录，不返回订单进度数据。
4. 客户甲同一客户公司下的另一个正常联系人，按现有公司共享订单规则检查查看权限。
5. 后台员工只查看其允许销售公司的任务；普通运营不能使用需集成管理员权限的处理按钮。

**通过标准：** 不能通过改订单内部 ID 越权。客户页面不显示 ERP 密钥、原始请求、长内部 ID 或技术报错正文。

### P11 已传 ERP 后改单或取消的边界

1. 仅使用本轮专用测试订单，在网站现有改单流程里提出、审核并接受一个变更；若已有出库，不通过绕过交付保护强行改单。
2. 后台检查 ERP Change / Cancellation Requires Review 的人工核对标记。
3. 客户进度页应提示修订单进度待团队确认，不继续把旧版本商品进度当成新版本结果。
4. ERP 原单不会被自动修改、取消或复制成新单；由 ERP 人员按既定人工流程处理，并记录两边差异。
5. 取消用例单独选择未实际发货的测试订单，验证取消后不继续自动刷新履约。

**通过标准：** 人工边界清楚，不重复下单、不错误串用旧进度。本项不能写成“ERP 自动改单闭环通过”。

### P12 技术异常扩展

以下可用隔离的接口模拟验证，需明确标注模拟，不能代替 P02 至 P06 的真实 ERP 业务操作。

| 异常 | 期望 |
| --- | --- |
| 同号不同 ERP 主表 ID、回查金额或客户不一致 | 停止自动认定成功，要求人工核对，不再次新增 |
| 报表混入另一订单主表 ID、物料串行 | 拒绝替换成功快照，不把他人数据展示给客户 |
| 已发大于订购、已发加未发不等于订购、无效数量 | 不使用不一致数据，后台说明原因，保留旧快照 |
| 以前已出现的报表商品行后来消失 | 不据此认定为零发货，要求核对，保留历史结果 |
| 报表超过当前安全单页上限或字段结构变化 | 不只显示第一页就声称数据完整；当前查询页大小为 500，超出安全范围会阻断 |
| 相同物料重复订单行且数量金额完全相同 | 不仅凭物料编码猜行；无法唯一绑定时记录待完善，不把同一进度复制到两个不同商品行 |

## 10 完成标准与收尾

可以宣布“网站下单至 ERP 创建通过”的条件：Demo 和银行达到确认条件的订单均成功下到 ERP，字段对照一致；未确认的报价不提前传单，尾款和重试不重复新增。

可以宣布“ERP 履约查询闭环通过”的条件：两个商品的供应、入库、第一批出库、补发结果都通过客户实际页面查看；每个商品的日期、累计已发和剩余数量准确，重复刷新稳定，多行和分批场景没有被待核验提示替代。

出现多行数量待核验、ERP 完整收货资料仍需人工补充或未执行异常用例时，必须在结论中列明，不能统一写“全部闭环通过”。可以分项验收，并列出人工补充操作和后续功能差距。

测试收尾：

1. 保存网站单号与 ERP 单号对照及证据，不在报告保留密钥、访问令牌或无关真实客户资料。
2. 恢复本轮临时配置；不要关闭已有正式业务所需的连接或更改真实客户付款模板。
3. 测试 ERP 单据、供应、入库和出库记录由 ERP 负责人按其审计流程处理；有下游单据后不能直接删除上游销售订单。
4. Odoo 已产生付款、会计分录或发货关联的测试订单也不能任意删除，按原生取消、冲销或归档规则处理。
5. 确认主客户以后仍能登录、查看保留的测试订单和已知进度；需要保留供后续查看的订单不要清理掉。

本轮不授权修改业务代码、向正式 ERP 组织新增单据、转账真实资金或自动执行 ERP 改单。发现问题先按第 9 节登记，再确认修复范围。
