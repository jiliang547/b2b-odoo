# Partner Hub 网站 AI 开发方案与验收规范

版本：V1.1

日期：2026-09-18

用途：开发范围确认、实现依据、测试验收和后续维护。

状态：设计方案，尚未实施。文中新增菜单、按钮、接口和模型均为拟开发内容，不代表当前已经存在。
代码核对基线：b2b-odoo / agent/figma-b2b-redesign / b7ba6de；本地 Odoo 19 Enterprise 20260805。Odoo.sh 的原生代码版本和能力需在开发第零阶段单独确认。

V1.1 修订：补充框架选型、长期上下文、知识检索与客户实际对话流程（第 21—24 节）。V1.0 已覆盖权限/价格/引用，但未充分定义长期会话记忆和工作流，本版将它们明确为第一期基础能力。本次仍仅修改开发文档，没有实施应用代码。

## 1. 方案结论

建设一个面向网站客户的 Partner Hub AI 应用，产品推荐、方案设计、招标分析和技术知识问答共用一个全站悬浮聊天入口和同一套客户身份、权限、资料、价格服务与项目记忆。客户不需要切换模式；不同能力由受控后台流程处理，不建设四个独立自主 Agent。2026-09-18 第一阶段仅开放产品推荐与知识问答，未实现的能力不显示为可用功能。

核心原则：

1. AI 负责理解需求、检索资料和解释推荐理由；Odoo 负责商品权限、价格计算、MOQ、客户归属、报价单和付款。
2. 客户在 AI 中看到的商品和价格，应与相同身份、网站、币种、型号、数量和地址条件下的正常购物流程一致。
3. 优先扩展 Odoo 原生 AI、Live Chat、产品资料和销售报价，不另建一套产品库、价格表或订单系统。
4. 通过服务端 API Key 调用外部模型；不在 Odoo.sh 中部署大模型推理服务。
5. AI 方案可以转入现有购物车，或由客户明确提交给运营审核；AI 本身不能批准客户、改价、确认收款、退款或发货。
6. 对资料不足、价格未配置、模型超时等情况提供明确退路，不编造、不泄露、不跳到原生报错页面。
7. AI 必须有受控执行/编排层：管理状态、检索、追问、校验和恢复；关键需求保存为结构化项目事实，不依赖聊天窗口长度或模型自行记住。

建议第一期交付“产品推荐 + 技术知识问答 + 客户权限价格一致性”；第二期交付“方案清单 + 报价审核闭环”；第三期交付“招标文件分析”。四项能力按同一架构规划，逐阶段验收上线。

## 2. 客户最终会如何使用

### 2.1 产品推荐

客户输入：Need speaker for airport.

系统先询问必要信息，例如使用区域、是否需要紧急广播、安装方式和环境条件。每次只问少量关键问题，不把聊天变成长表单。

返回：

- 符合需求且客户有权查看的产品。
- 选型理由、适用条件、尚未确认的事项。
- 必需配套与可选配套，明确区分，不擅自加购。
- 对应型号的 Datasheet 或产品链接。
- 有价格权限时展示客户实际价格、币种、数量条件和 MOQ；没有权限时不显示金额。
- View Product、Ask a Question，以及条件满足时的 Add to Cart。

机场、消防广播等涉及安全和认证的用途，只能提供有资料依据的初选建议；无证据的认证不得声称满足。

### 2.2 方案设计

客户输入：School, 24 classrooms, need paging.

系统需要进一步确认每间教室的面积、扬声器数量假设、分区需求、音源、网络条件等。仅凭“24 间教室”不能直接认定需要 24 个扬声器。

输出一份可编辑方案：

- 项目需求摘要和已确认条件。
- 仍待确认的假设。
- 产品清单：明确型号、用途、数量、单位、必要/可选。
- 功放容量、负载、分区、接口等兼容性检查结果。
- 资料出处及限制。
- 有权查看价格时的产品费用预估；未知运费或税费单独标记，不默认为零。
- 客户可修改数量、删除可选项，再选择加入购物车或提交报价审核。

涉及功率、数量、合计的确定性计算由服务端规则完成。模型只能提议参数，不能凭语言判断替代计算。需要专业声学、布线或法规确认的内容交给工程人员。

### 2.3 招标分析

客户上传 Tender，并选择“仅分析 Lucky Tone 产品”或允许的产品品牌范围。该选择只是缩小范围，不能扩大客户原有商品权限。

系统逐条列出：

| 招标要求 | 候选产品 | 判断 | 产品证据 | 缺口/下一步 |
| --- | --- | --- | --- | --- |
| 从招标原文提取，保留页码或章节 | 可访问的真实型号 | Meets / Partially Meets / Does Not Meet / Not Verified | Datasheet 版本、页码或章节 | 配套条件、缺失证据或人工确认 |

特别规定：

- “资料中没有找到”属于 Not Verified，不等于明确不满足。
- 明确有参数冲突时才可判 Does Not Meet。
- 认证、兼容性、质保和交货承诺不得根据常识补写。
- 说明文件已处理多少页、哪些页无法识别，不允许将部分分析包装成完整结论。
- 分析报告不是企业正式投标承诺；正式响应必须人工复核。
- 上传文件默认仅上传者及有权处理该申请的内部人员可见，不自动进入公共知识库。

### 2.4 技术知识问答

客户输入：How to connect Dante?

优先要求确定设备型号和软件/固件版本，再根据已审核资料解释连接步骤、限制和排查方法，附文档来源。

没有可靠资料时明确说明并提供联系技术支持入口。产品专有事实不依赖模型记忆；泛用知识必须与产品已验证能力区分。

## 3. 范围及不做事项

### 3.1 本项目范围

- 客户网站 AI 界面、会话、四个业务入口。
- 现有产品/资源检索与访问控制。
- 现有客户定价的实时查询和展示。
- 方案保存、明确确认后加入购物车或申请报价。
- 资料审核、索引状态、运行监控和成本限制。
- 转人工、错误兜底、浏览器实测及权限回归。
- 后台配置说明、运营操作手册和上线检查表。

### 3.2 暂不做

- 自建模型训练平台、GPU 服务或独立 ERP。
- 自动给客户审批、分公司、改客户类型或调整价格表。
- AI 自主议价、承诺折扣、赠品、账期、税率或交期。
- 自动确认正式销售订单、发票、银行到账、付款、退款和发货。
- 直接修改已提交、已付款或改单中的订单。
- 绕过现有价格权限生成报价 PDF。
- 自动抓取整个互联网或整库读取所有后台资料。
- 把客户上传的招标文件用于其他客户问答或模型训练。

未来需要订单查询等功能，应以单独受控工具扩展，而不是给 AI 开放所有模型访问能力。

## 4. 当前系统中必须沿用的业务规则

### 4.1 区分三种“公司/品牌”

| 概念 | 当前用途 | AI 必须如何处理 |
| --- | --- | --- |
| 客户公司 | 客户所属的商业联系人，即 commercial_partner_id | 识别审批、Segments、客户类型和专属价格 |
| 销售公司 | 实际合同、收款、发票所属的 res.company | 由现有客户品牌/销售公司路由确定 |
| 商品品牌 | 商品本身属于哪个品牌 | 用于推荐与筛选，不决定订单销售主体 |

例如：A 品牌归属客户可以买网站内其他获授权品牌的商品，但订单仍按其绑定的销售公司处理，不能按每个商品的品牌分裂合同和收款主体。

不得使用后台操作员右上角当前公司、网站基础公司或模型猜测作为客户销售主体的替代值。客户品牌与销售公司配置缺失时，引导联系运营处理。

### 4.2 客户类型与价格表

现有客户分类继续使用：

- Distributor / Importer
- System Integrator
- Installer / Contractor
- Retailer / E-commerce
- Brand Owner / OEM Customer
- Consultant / Designer
- End User / Project Owner
- Other

使用当前有效价格表机制：客户类型基础价格 + 按现有优先级匹配的公司专属覆盖。

不是“多张表取最低价”，也不是“把多个折扣连续叠加”。当前代码按 priority、id 顺序匹配专属层；数值较小的 priority 优先，命中适用规则后使用该层，其余按现有基础层和原生规则处理。当前专属覆盖中的全局规则不用于遮盖客户类型基础层；AI 不另行解释这些规则。

未配置必要基础价格时沿用 pricing_pending 行为，不能退回公开零售价、其他客户价格或其他销售公司的价格。

### 4.3 可见性与价格是两个独立权限

- 价格表中存在某商品，不代表客户获得该商品的查看权限。
- 商品可见，不代表客户可以看价格或下单。
- 商品资料也有独立的发布和可见性规则。
- 同一客户公司联系人可复用公司级商业配置，但私人 AI 会话和上传文件不因此默认共享。

## 5. 原生复用与技术架构

### 5.1 复用边界

| 能力 | 首选复用 | 本项目需要补充 |
| --- | --- | --- |
| AI Agent、Topics、Sources | Odoo 19 原生 AI | 网站专用 Agent、受控工具、资料范围 |
| 模型连接和 Key 配置 | 原生 Provider 适配范围内复用 | 非原生接口才新增小型适配器 |
| 在线会话与转人工 | 原生 Live Chat / Discuss | 网站设计适配、私有上下文和业务卡片 |
| 产品、变体、文件 | 原生产品、product.document、ir.attachment 及现有 B2B 资源 | 参数完整度提示和可检索字段 |
| 价格与 MOQ | 现有 b2b.product.service、有效价格表、原生销售计算 | 安全的 AI 工具封装 |
| 报价及付款 | sale.order 和现有审核、银行/在线支付 | 来源标记、幂等、方案与报价关联 |
| 权限、活动和通知 | Odoo 权限组、记录规则、mail.activity、现有 Message Center | 仅必要的 AI 资源权限和转人工衔接 |

原生 AI 已有 Agent、Topics/Tools、资料 Sources 等配置概念；原生 AI Live Chat 可接入网站并转人工，不需要重新制造一套基础客服引擎。具体扩展接口仍以目标环境安装版本为准。[原生 Agent 文档](https://raw.githubusercontent.com/odoo/documentation/19.0/content/applications/productivity/ai/agents.rst)、[原生 AI Live Chat 文档](https://raw.githubusercontent.com/odoo/documentation/19.0/content/applications/productivity/ai/live-chat.rst)

### 5.2 拟新增应用

建议主模块命名 b2b_ai，应用显示为 Partner Hub AI。

- 以 Odoo 扩展模块实现，不修改 Odoo 原生源码。
- 集中放置网站权限包装、业务工具、前端卡片、结构化方案及验收测试。
- 安装该应用时由依赖声明安装必要原生模块；具体依赖在第零阶段确认。
- 首次安装保持“客户入口未启用”，管理员配置 Key、资料和预算并通过自检后启用。
- 不在本轮设计阶段把 AI 强行设为现有 b2b_website 的安装前提。
- 仅当模型供应商不兼容原生连接能力时增加独立 Provider 适配扩展；不要为四个业务入口建立四套连接器。
- Documents、Knowledge 等可选桥接模块仅在实际使用相关资料来源时依赖，不无差别安装应用。

如目标 SH 无法使用原生 AI，必须先确认替代架构及依赖后再建模块，不在一个清单里假装依赖可以动态忽略。

### 5.3 请求处理顺序

一次业务回答必须按以下顺序执行：

1. 网站服务端识别真实登录用户或匿名会话。
2. 解析网站、客户商业公司、销售主体、语言、币种和权限状态。
3. 从授权范围内检索商品、参数和资料。
4. 模型理解需求、提出候选产品或解释资料。
5. 服务端校验模型返回的产品/变体/引用 ID，丢弃无权限或不存在的数据。
6. 需要价格时，按当前数量和业务上下文调用现有定价服务。
7. 服务端生成产品和报价卡片；客户看见的交易金额不由模型自由文本生成。
8. 涉及写操作时，客户在网站确认后走独立业务入口并再次校验。

技术要点：资料必须在进入模型上下文之前过滤；不能先把全库发给模型再要求它“不要泄露”。

### 5.4 Odoo.sh 与模型 API 的可行性边界

通过服务端调用外部模型 API 的方式适合本项目；模型运算发生在供应商侧，并不需要在 SH 中自建推理容器。Odoo 官方说明，SH 使用原生 AI 需要配置 API Key，原生文档列出的供应商为 OpenAI 和 Gemini。用户实际 Key 所属服务是否兼容，需要单独验证。[原生 AI Key 文档](https://raw.githubusercontent.com/odoo/documentation/19.0/content/applications/productivity/ai/apikeys.rst)

重要兼容性风险：

- 本地原生 ai 模块的安装钩子检查 PostgreSQL vector 扩展；知识库检索使用向量索引。
- SH FAQ 同时对自行安装数据库扩展、额外常驻进程及长连接有一般限制。
- 因此不能仅凭“使用 API Key”就保证原生知识库在目标 SH 构建必然可安装，也不能仅凭一般限制断言官方 AI 必然不能用。
- 第零阶段必须在目标 SH 测试构建验证原生 AI 安装、资料索引、检索和问答；必要时向 Odoo 确认平台支持。
- 不自行在 SH 安装数据库扩展二进制或常驻向量服务。
- 原生方案不可用时，先保留受控产品查询能力；再评估外部托管检索服务，并单独确认数据传输和成本。不能静默降低为无证据的知识问答。

部署约束和定时任务限制参照 [Odoo.sh FAQ](https://www.odoo.sh/faq)。这部分是上线门槛，不是已完成的兼容性测试结论。

## 6. 客户权限与价格展示

### 6.1 权限决策矩阵

下面是拟定的 AI 能力边界。商品和价格最终资格均调用现有网站规则；如果网站配置为始终显示价格或始终隐藏价格，AI 必须与之保持一致，不另写一份相冲突的规则。

| 访问者状态 | 推荐/资料 | 金额 | 方案与报价动作 |
| --- | --- | --- | --- |
| 未登录 | 仅公开范围 | 按现有公开价格策略；默认不新增价格授权 | 可讨论需求；保存私人方案、上传 Tender、申请交易报价前登录 |
| 已注册但待审批 | 仅现有允许范围 | 按现有审批及显示策略 | 可咨询/联系运营，不能通过 AI 绕过下单审核 |
| 已审批，但价格或销售主体配置不完整 | 允许范围内推荐 | 不返回可交易金额；标记配置中 | 可保存需求、请求人工帮助，不创建可付款报价 |
| 已审批且定价正常 | 允许范围内完整服务 | 本客户当前有效价格 | 校验后可加购、申请报价 |
| 内部员工测试客户体验 | 必须指定模拟客户并有相应权限 | 按该客户上下文，不继承管理员可见所有数据的特例 | 默认只读预览，不冒用客户提交或支付 |

是否允许下单还应复用现有结账资格检查，不能仅根据 can_view_price 为真就开放所有交易动作。

### 6.2 价格计算合同

每次询价至少固定：

- 网站和真实客户身份。
- 客户商业公司与销售公司。
- 币种、有效价格表、规则有效日期。
- 明确产品变体、数量、销售单位和适用 MOQ。
- 税务位置、开票/送货地址等已知条件。
- 是否已有人工发布的报价、报价有效期与版本。

实现要求：

1. 商品目录展示可复用 price_payload；它是目录价入口，不足以直接代表任意数量和变体的整单报价。
2. 任意数量的方案预估须复用原生价格规则、变体差价、单位及税额计算，不能拿目录单价简单乘数量冒充整单总额。
3. 运费未核算时显示 Shipping to be confirmed；税务信息不足时显示 Tax to be confirmed。仅产品小计已知时不标为最终应付总额。
4. 定金、尾款和付款条款继续由现有收款流程计算；模型不把“订单总额”当作“本次应付金额”。
5. MOQ、数量步长使用现有 procurement_info / validate_sale_quantity；当前购买步长并非直接等于原生单位 rounding。
6. 不足 MOQ 时提示所需数量，客户确认后再调整；不能偷偷把 1 件变成 10 件。
7. 不向模型提供成本、毛利、供应价、其他客户价格、全量价格表或内部折扣权限。
8. 模型可说明“你的账户价格已应用”，但无需暴露内部定价层和规则名称。
9. 使用已配置币种和价格表，不把模型计算的汇率报价作为可购买价格。

### 6.3 价格快照与有效性

- 卡片显示币种、数量条件、是否含税、估算/报价状态和更新时间。
- 新方案预估、加购、提交报价前重新检查权限和当前价格。
- 刷新后金额发生变化时展示差异，要求客户确认，不直接按旧卡片写入订单。
- 对已由运营发布的有效原生报价，遵循现有报价锁定/改单流程，不因 AI 会话刷新擅自重算改价。
- 历史对话中的金额标注为历史快照；不代表当前仍有效。
- 客户公司、品牌归属、审批或价格权限改变时重新验证会话和附件访问；不得继续输出旧授权范围内的上下文。

第一期不缓存个性化最终金额。若后续必须缓存，键至少包含客户身份/商业公司、网站、销售公司、币种、商品变体、数量、单位、税务地址上下文和规则版本，并考虑规则到期时间。不能只用产品 ID 缓存。

## 7. 方案、购物车与报价闭环

### 7.1 三种东西必须分清

| 类型 | 用途 | 是否销售承诺 | 是否可支付 |
| --- | --- | --- | --- |
| AI 方案/预估 | 沟通需求和初步产品清单 | 否 | 否 |
| 已提交的原生待审核报价 | 运营核对型号、数量、费用和条款 | 尚待审核发布 | 否 |
| 已审核发布的原生报价 | 按原有报价有效期和条款执行 | 以报价文件及条款为准 | 仅在现有支付规则允许时 |

AI 生成的方案文档必须明显标识 Draft Proposal；不能伪装成已经批准的 PI 或正式报价。

### 7.2 路径 A：客户自己下单

AI 推荐/方案 → 客户确认型号和数量 → Add to Cart → 原有购物车与结账。

- 完整沿用原来的在线支付、提交订单审核、银行转账/约定付款流程。
- 已有购物车时显示即将增加哪些行和数量；不覆盖现有行，不未经确认清空购物车。
- 同款产品合并后的数量必须重新计算 MOQ 和价格阶梯。
- 当前购物车主体不一致、已有待处理支付或不可编辑时，按现有规则阻止或引导处理，不偷偷换公司。
- 加购成功后卡片金额以服务端结果刷新。

### 7.3 路径 B：提交给运营报价

1. 客户确认方案清单，选择 Request a Quote。
2. 显示提交预览：客户公司、销售主体、币种、产品与数量、已知金额、未确认费用、项目备注。
3. 必要地址或变体未选全时先补齐；无价格配置或无下单资格则转为人工咨询，不假造销售金额。
4. 客户确认后创建或关联一个原生 sale.order；报价先进入现有待审核流程。
5. 服务端设置当前原有审核状态与付款限制，并给有权限的运营安排原生活动。
6. 运营检查清单，必要时联系客户，核算运费和其他费用。
7. 有权限人员发布报价，客户在 My Quotations 中查看。
8. 客户沿用现有在线/银行转账方式付款，后续定金、尾款和订单状态沿用既有机制。

技术实现注意：

- 当前待审核入口 /shop/submit-for-review 使用原生报价 sent 状态和 b2b_review_state=pending；不能只创建一张 draft 单就声称已进入运营审核队列。
- 开发时将可复用的提交审核业务整理为小型服务，由现有结账入口与 AI 入口共同调用；不要在 AI 模块复制控制器中的整段审核逻辑。
- 保留原生字段含义：action_quotation_sent 的调用不等于已经给客户发送了报价邮件；通知需走明确的现有消息流程。
- 发布复用 action_b2b_mark_review_ready 及收款相关扩展；必须实测不同付款条款下的本次应付金额，不自行硬编码全款或定金。
- 创建过程须具备事务原子性、报价行服务端计价和幂等键；网络重试、双击只能得到同一份报价结果。
- 已提交后需要改动，回到现有报价编辑/改单流程，不能由 AI 覆盖已发布价格。

### 7.4 运营与客户的提示

- 提交成功：Your request has been sent to our sales team for review.
- 运费未定：Our team will confirm shipping and the final amount before payment.
- 价格配置中：Your pricing is being configured. Please contact our team.
- 不允许用“订单已确认”描述一份刚提交的待审核报价。

这些文案使用网站翻译机制维护；英文为默认界面语言，不写死中文。

## 8. 知识库、产品资料与招标文件

### 8.1 不建第二套产品台账

产品名称、SKU、变体、品牌、Applications、参数、MOQ 和文件继续在现有产品/资源界面维护。AI 引用原记录，不要求运营复制一份“AI 产品”。

开发初期先盘点参数完整度；必要字段尽量复用原生属性和现有字段，确实没有适合位置时才加结构化技术字段。文本 Datasheet 用来提供证据，不能替代全部可校验的兼容参数。

建议按业务需要补齐：型号、类别、安装方式、协议/接口、功率及负载条件、分区/通道、适用环境、配套关系、认证证据和文件版本。不是每类商品都强制填写全部字段。

产品配套推荐不能仅靠关键词相似：优先复用现有可选产品/配件关系，辅以经过审核的兼容规则；复杂搭配允许人工维护少量约束。

### 8.2 资料分类

| 资料范围 | 典型内容 | 处理方式 |
| --- | --- | --- |
| 公开资料 | 已公开手册、公开 FAQ | 仅在原有发布权限允许时可供游客使用 |
| 审批客户/Segments 资料 | 指定产品文件、受限技术资料 | 检索前按真实用户逐次过滤 |
| 客户私有资料 | Tender、项目需求、私有方案 | 默认上传者隔离；不加入公共 Agent 的全局 Sources |
| 内部资料 | 成本、供应商合同、内部故障记录 | 默认不提供给客户 Agent |
| 交易动态数据 | 价格、收款、订单状态 | 按需经受控工具查询，不放入公共向量知识库 |

内部希望开放某份技术资料时，先形成可对外版本，经授权发布后再索引，而不是让 AI 自动“去掉内部内容”。

### 8.3 来源管理与更新

优先扩展原生 Sources 的处理/索引状态。每份对外资料须可识别：

- 原始产品/资源记录、附件、品牌和访问范围。
- 标题、语言、型号范围、版本/生效日期。
- 发布/审核状态、文件校验值、索引版本。
- 引用定位：PDF 页码；无页码格式使用章节/段落。

上传、替换和撤下后的处理要求：

1. 发布未完成或索引失败的资料不能当作已可用证据。
2. 替换文件后失效旧片段；切换向量模型时安排重建，不能混用不同向量空间。
3. 撤回可见性后立即禁止检索及下载，不能等定时清理后才失效。
4. 原始文件相同可去重存储，但内容哈希相同绝不代表两个客户的授权相同。
5. 每个检索片段必须能追溯到当前允许的原始记录；原生索引的去重或共享行为也需通过隔离测试。
6. 引用链接通过现有受保护下载入口生成，不暴露可绕过检查的永久公共链接。

### 8.4 Tender 处理

第一版承诺支持可提取文本的 PDF；DOCX、扫描 PDF、图片表格和 OCR 能力在第零阶段逐项验证后才开放。前台不能宣称支持一个实际上解析不了的格式。

处理流程：权限与限额检查 → 文件校验 → 提取文本和版面定位 → 条款拆分 → 检索允许的产品证据 → 逐项判定 → 汇总人工复核报告。

建议试运行初值：每次一个文件，20MB、100 页上限；这些是产品建议值，需结合 SH 性能和实际供应商限制压测后确认。超限应在页面明确拒绝，并支持客户拆分文件或联系销售。

具体规则：

- 检查扩展名、实际文件类型和内容可解析性；拒绝空文件、伪装文件、超限和无法解密的文件。
- 不执行宏、脚本或文件内命令，不跟随文件内任意外链。
- 文件安全检查能力单独确认；没有接入恶意文件扫描服务时，不声称“已完成病毒扫描”。
- 上传内容视为待分析资料，而不是系统指令；文件中要求导出客户数据、改报价或忽略规则的文字不得执行。
- 输出应区分“招标原文”“产品证据”“模型推断”和“人工确认”。
- 所有强制性条款必须有结果或明确待处理项，不可静默漏项。
- 导出报告使用服务端受控模板，保留版本、生成时间、来源及 Draft 标记。

## 9. 开发接口与工具合同

以下工具名称是建议接口名，不是当前已有方法。所有接口由服务端决定可执行范围，不能靠提示词替代权限。

### 9.1 模型可用的只读工具

| 工具 | 模型可传参数 | 服务端固定/校验 | 输出 |
| --- | --- | --- | --- |
| search_products | 需求关键词、应用条件、允许的筛选项、分页 | 网站、用户、客户公司、可见域、最大返回数 | 允许的产品 ID 与必要技术摘要 |
| get_product_details | 产品/变体 ID | 存在、已发布、可见、变体属于产品 | 技术参数、适用限制、授权资料 |
| get_purchase_conditions | 产品/变体 ID、数量 | 当前有效价格表、MOQ、购买资格 | 可购买状态、MOQ/步长、受控价格结果 |
| search_knowledge | 问题、当前允许的型号范围 | 检索前过滤来源与文件权限 | 片段和证据引用 |
| validate_solution | 建议的型号、数量、连接关系 | 正数、单位、兼容规则、资料依据 | 通过项、阻止项、待工程确认项 |
| get_analysis_status | 分析任务标识 | 所有者、网站和任务权限 | 进度、结果或安全错误 |

get_purchase_conditions 的金额结果优先直接送前端卡片；如某项解释确需给模型，仅传本次授权结果，不传全量价表。总体费用由服务端算，模型不自行汇总。

### 9.2 由客户明确操作触发的业务动作

| 动作 | 必要确认 | 结果 |
| --- | --- | --- |
| 保存方案 | 登录及当前方案所有权 | 保存结构化草案，不创建销售订单 |
| 加入购物车 | 确定变体、数量及更新后的金额/购买条件 | 调用现有购物车逻辑 |
| 提交报价审核 | 预览项目、地址、清单、销售主体与未确定费用 | 一张原生待审核报价 |
| 转人工 | 同意转交的摘要、联系资料和文件范围 | 现有咨询记录或技术支持工单 |
| 上传并分析 Tender | 明示文件处理说明并由客户提交 | 私有分析任务 |

第一版不开放“模型自己调用写工具即成功写入”的路径。模型最多提出按钮，真正执行必须经过独立的用户确认接口；复制一句“我同意”或文件中的命令不能伪造确认事件。

### 9.3 受控输入和输出

请求可接受：产品变体 ID、数量、方案版本、用户选择的可用币种标识及幂等标识。

请求不得决定：partner_id、commercial_partner_id、company_id、任意 pricelist_id、price_unit、discount、tax_id、用户权限、订单确认状态。地址 ID 只能从当前用户原本有权使用的地址中选择。

价格卡片最少包含：

- 服务器确认的 product/variant、数量、单位。
- state：priced / login_required / approval_pending / pricing_pending / unavailable。
- priced 时才有金额、币种、税费/运费说明。
- 价格上下文版本、计算时间、方案版本。
- 允许的动作与不可执行原因。

金额不可用时返回空金额及原因，不用 0 代替。服务端再次计算和验证，不信任客户端回传的卡片金额或签名令牌中的旧价格。

对任意无权访问的 ID 使用统一安全结果；不得通过错误信息泄露其他客户的记录名称、金额或文件名。

## 10. 网站交互设计

### 10.1 入口

- 主入口：网站右下角 AI Assistant 悬浮按钮；非模态聊天窗，不跳转独立 AI 页面、不展示模式切换。旧页面链接兼容跳转到首页并打开窗口。
- 产品页入口：Ask about this product，带入当前产品上下文，不带入管理员身份。
- My 页面：My AI Projects，查看本人方案、招标分析和相关报价；这是新增入口建议。
- 全站小窗：本期采用原生 OWL public component、资源包和 cron；保留私有会话及权限服务，不额外引入 React 或人工客服频道。后续接人工客服再评估 Discuss/Live Chat，不同时维护两套 AI 历史。
- 资料/报价下载保持网站现有视觉和权限，不能打开后台模型列表页。

### 10.2 页面组成

顶部提供历史、新对话、需求编辑、展开和收起；中间为对话、资料引用和商品卡片；底部固定输入框。移动端自适应为大面板，不横向拖拽。普通整页导航后恢复当前会话/草稿/开合状态；后台任务生成回复，不依赖当前页面存活。

重要体验：

- 区分发送中、正在检索、文件处理中、等待补充信息和完成。
- 每次只提出关键澄清问题，可先展示有依据的候选方向。
- 清单可增删和改数量；重算后说明变化。
- Add to Cart、Request a Quote 等按钮只在允许时显示或提供明确禁用原因。
- 长任务可离开页面后返回查看，不因刷新丢失。
- 页面使用现有按钮、提示、弹层和翻译机制；按钮处理前后位置/大小不跳动。
- 成功提示短暂浮动；需用户处理的错误持续可见，不能 3 秒就消失。
- 支持键盘、可见焦点、读屏状态、移动端文件选择。

### 10.3 错误与转人工

统一错误分类：

| 情况 | 客户界面行为 |
| --- | --- |
| 登录过期 | 保留非敏感输入，提示重新登录；不弹含 Odoo 字样的原生错误 |
| 审批/价格未就绪 | 显示当前状态和 Contact Us，不重复尝试获取价格 |
| 无适合商品/无证据 | 明确说明未找到符合条件的产品，允许调整需求或转人工 |
| 模型超时/限流/余额不足 | 显示安全的暂不可用文案和重试/联系销售 |
| 文件不支持/内容不完整 | 提示具体可纠正原因，不空白失败 |
| 价格或权限变化 | 显示方案需要刷新，确认后再继续 |
| 未知故障 | 站内错误卡片或品牌化错误页，显示追踪编号，不显示堆栈和 Key |

转人工优先复用当前 Contact Requests、销售报价沟通或 Helpdesk。销售选型交销售，技术故障交售后。CRM 如未用于当前流程，不为 AI 强制增加一套待办入口。

只在客户要求转人工或流程确需人工时建立记录；AI 的每句对话不应变成后台 Message Center 未读消息。转交后通过现有站内消息和邮件规则通知，不重写双通道消息系统，也不宣称邮件必定送达。

## 11. 数据模型和权限组设计

### 11.1 最小必要数据

| 数据 | 实现建议 |
| --- | --- |
| 模型、Agent、Topics、知识来源 | 优先原生 AI 对象及扩展字段 |
| 会话和消息 | 优先复用原生 Discuss/Live Chat；补充模式、所有者、网站、当前项目与有版本的需求状态；聊天摘要不能替代结构化事实 |
| 结构化项目 | 拟建 b2b.ai.project，记录需求槽位、来源、确认状态、假设、方案版本、状态和关联报价；从第一期支持保存项目需求，不等到正式报价阶段才有记忆 |
| 清单行 | 拟建 b2b.ai.project.line，关联真实产品变体和数量，不另建产品台账 |
| 招标分析任务 | 拟建 b2b.ai.analysis，关联私有附件、条款结果、证据和处理状态 |
| 调用审计 | 优先复用可用原生日志；不足时只补最小元数据和错误追踪 |
| 销售报价 | 原生 sale.order，补 AI 来源关系；不建 AI 专用订单模型 |

结构化清单中的价格只作为带时间及上下文的历史快照，不是新的定价来源。方案说明是保存后的业务摘要，不要求或保存模型的隐藏推理过程。

数据所有权至少记录：创建者、客户商业公司、网站、相关销售公司；访问检查仍以当前资格为准，不能仅凭创建时快照永久放行。

### 11.2 角色安排

- 网站客户：自己的会话、项目和上传文件；已有报价遵守现有 Portal 访问规则。
- 运营/销售：根据现有 B2B 和销售权限处理转交需求、编辑报价；AI 权限不得额外授予改价或收款能力。
- 技术/资料维护人员：按职责审核知识资料；默认不能查看所有客户 Tender。
- B2B Manager：按现有权限发布待审核报价和管理业务范围；不会因此自动获得服务器 Key。
- 系统管理员：模型连接、Key、工具白名单、预算、启停和诊断。

继续在 Odoo 原生用户/权限组页面分配权限。必要的“AI 配置/资料发布/私有任务处理”能力采用少量原生组或现有组扩展，不增加第二套独立人员权限系统。具体映射开发时审计现有组继承关系后确定，不把所有内部员工一律视为 AI 管理员。

后台服务账号或定时任务即使具有较高权限，返回结果前也必须以原始请求者重新检查；不得用 sudo 的身份执行网站商品可见性分支。

## 12. 安全、隐私和成本控制

### 12.1 必须落到代码里的防护

- 接口逐次校验用户、会话、项目、文件、报价和销售公司关系。
- 不开放通用 ORM、任意 SQL、执行 Python、任意服务端动作等工具给客户 Agent。
- 产品、价格和文档查询使用字段白名单，限制返回数量、文本长度和工具调用次数。
- 所有写入口有 CSRF 防护、真实操作确认、幂等和审计。
- 输出 Markdown/HTML 经过安全渲染；拒绝脚本、危险链接及模型伪造的下载地址。
- 知识内容、网页、产品描述和 Tender 中的指令都属于不可信数据。
- 客户 URL 不直接交给服务器访问；外链摄取只允许管理员审核的来源，防止访问本机、内网或云元数据。
- API Key 仅服务端受限配置；不进 Git、前端、提示词、普通日志或截图。
- 不声称 Odoo 默认参数存储天然加密；按实际部署选择受保护配置或环境秘密，并限制数据库/备份访问。
- 从生产克隆测试库后主动禁用自定义 AI 外呼及自动索引；不能假设 SH 自动清除了自定义 Key。
- 客户退出、切换账号、审批撤销、转公司后清理浏览器缓存和会话上下文，防止同设备串号。

即使 native Agent 有“Restrict to Sources”选项，也仍需程序级访问控制和引用校验；提示词不是安全边界。

### 12.2 文件和供应商数据处理

- 上传前说明文件会发送至已配置 AI 服务进行分析，以及用途和删除入口。
- 实际供应商、数据保留、训练使用政策、区域和分包方在上线前确认；不能默认所有 API 供应商都不留存。
- 默认不把历史订单、联系人地址、内部备注随问题全部发送，只传任务所需的最小内容。
- 客户私有文件不跨用户训练或共享；如未来提供公司内共享，必须增加明确授权和界面提示。
- 设置会话/临时文件/分析报告保留期、人工保留例外与删除规则；具体周期由运营确认。
- 删除应覆盖原附件、索引、缓存和供应商文件副本（若使用）；备份中的保留限制向管理员说明，不能承诺即时删除所有备份。
- 日志默认只保留请求 ID、模型、耗时、用量、状态和必要业务引用，不记录完整 Tender、Key 或全部对话。

### 12.3 费用和流量

建议试运行默认值，需压测及预算确认后生效：

- 默认仅登录客户开放文件分析；游客公开问答单独限额。
- 每会话同一时间一个生成请求，每账户同一时间一个文件分析任务。
- 单请求限制输入长度、检索片段数、工具调用轮次和最大输出量。
- 单账户日限额、网站总额度、供应商侧额度三层控制；金额未知时以 token/次数硬上限兜底。
- 成本展示区分对话、Embedding、OCR/文件分析和存储，不能只统计聊天 token。
- 达到限额时停用 AI 生成，仍保留正常购物和联系销售能力。
- 对无效请求在调用模型前拒绝，避免攻击者用错误 ID 消耗额度。
- 若复用 Turnstile，需保障失败可以在当前页面恢复；它不能代替服务端限流。

预算是待配置项，本文不假设供应商费率或承诺月费用。

## 13. Odoo.sh 运行方式与稳定性

### 13.1 对话请求

短问答采用有明确超时的请求。试运行可将单次模型调用上限设为约 20 秒，但必须低于目标 SH 的实际请求预算，并为权限、检索和渲染预留时间；上线前以压测调整，不承诺固定响应速度。

第一版不依赖额外常驻进程或无限长流式连接。原生流式能力如要使用，必须在目标 SH 验证断线、重连和代理行为。普通加载状态即可，不为了逐字输出增加不稳定链路。

只对可安全重复的临时读失败进行有限退避重试；写订单动作不盲目重试。重试仍计入总超时与费用预算。

### 13.2 文件分析与资料索引

- 长任务拆分为可恢复的小批次，持久化进度，不在一次 HTTP 请求里读完整本大标书。
- 优先评估原生索引任务和有界定时任务，记录 queued / processing / completed / failed / cancelled。
- 任务恢复时重新验证所有者权限，采用任务占用标记与幂等，防止两个执行器重复生成结果。
- 阻塞式 HTTP 调用不跨长时间持有订单等业务锁。
- SH 测试环境的定时任务行为与生产不同；必须展示排队状态，不能保证文件上传后立即后台完成。
- 如果原生调度达不到可接受的交互时延，才引入受管外部异步处理；需额外评审，不偷偷增加运维系统。
- 如引入外部回调，必须校验签名、任务归属、结果版本和重复回调，不能根据回传 company_id 决定写入对象。

不把社区 queue_job 或其他常驻队列作为未经验证的 SH 默认方案。

### 13.3 故障隔离与升级

- 提供网站级、入口级和文件分析级开关，出故障可以单独关闭 AI。
- AI 不参与购物车正常计价和支付结果确认的必经路径。
- Key 失效、供应商故障、知识索引失败均不得使首页、登录、产品、结账不可用。
- 配置更新和升级脚本幂等，不覆盖管理员已维护的 Key、资料和提示词。
- 依赖 Odoo 私有方法的代码集中在小型适配服务；升级时做契约测试，不散布全站。
- 提示词、工具定义、模型版本和知识来源版本可追踪；修改后先跑评测集再推广。
- 不保存无用途的框架、示例页面和测试入口到生产导航中。

## 14. 后台配置与日常维护设计

### 14.1 初始化向导建议

在 Partner Hub AI 后台提供四步配置，入口汇总现有设置，不重复保存同一份配置。

| 步骤 | 管理员操作 | 完成标准 |
| --- | --- | --- |
| 1. Connect Model | 选择供应商/模型，安全填写 Key，必要时配置已批准的 Base URL | 对话、结构化输出和所需 Embedding 分别测试通过 |
| 2. Select Knowledge | 选择已审核的现有产品文件/技术资料，检查权限 | 可索引资料完成，失败资料有原因 |
| 3. Set Access & Limits | 选择入口、游客策略、预算、人工接收人和文件限制 | 权限隔离、配额和转人工测试通过 |
| 4. Preview & Enable | 用指定测试客户预览价格与流程 | 完成上线门槛，最后启用前台入口 |

不要把客户类型、价格表、品牌收款账户再复制到 AI 设置中。该处只显示当前状态和返回原配置界面的入口。

### 14.2 模型接口尚待确认的内容

- 供应商名称，是否官方接口或兼容网关。
- Base URL、允许模型，以及工具调用/结构化输出是否可靠。
- 文档检索所需 Embedding 是否另有模型、凭证或计费。
- 可处理文件类型、上下文限制、区域和数据保留。
- 单次/并发限制、预算及出错响应结构。

Key 由管理员在受限设置中填写，不需要粘贴进聊天、开发文档或仓库。

仅有一个可以聊天的 API Key，不代表它同时支持 Embedding、OCR、文件解析和原生 Agent 的全部协议。这些能力分别验证；能用原生接口则不开发通用网关。

### 14.3 运营日常工作

1. 正常维护产品、型号、参数和文件，不再维护 AI 价格表。
2. 发布资料后查看索引状态，失败时按具体原因处理。
3. 从原有消息/报价待办接收 AI 转交的客户需求。
4. 正常核对报价、运费和条款，并按原有权限发布。
5. 每周检查无答案问题和客户反馈，补资料或纠正不准确内容。
6. 技术人员审核高风险场景和招标结论。
7. 管理员检查调用量、错误率和费用；先调整资料/范围，再考虑更换模型。

后台“预览为客户”必须明显显示正在模拟哪个客户，避免管理员看到的价格被误认为普通客户价格。

## 15. 分阶段开发与交付

### 第零阶段：可行性验证和边界冻结

交付一份实际验证记录，不开发完整前台。

必须验证：

1. 目标 SH 原生 AI 能否安装，vector 依赖是否由平台满足。
2. 用户实际模型接口的对话、结构化返回、工具调用和 Embedding。
3. 一个真实产品文件索引/检索并返回可追溯证据。
4. 公共与私有资料隔离，包括同内容不同权限的文件。
5. 两个不同客户看到不同价格，但同客户结果与网站一致。
6. 测试环境外呼开关、调用预算和超时行为。
7. 当前网站错误处理和 Live Chat/Message Center 复用方式。
8. 依赖模块、许可条件、文件解析范围和备选路径。
9. 超过原生默认历史窗口的多轮追问、跨天恢复、需求改动、模式切换和过期回答拦截。
10. 原生 AI 扩展方案是否能通过第 21 节编排门槛；不通过时对 LangGraph 做小范围对照原型并记录选型结论，不同时开发两套正式运行链路。

未通过的能力明确标记，决定使用原生还是受管外部补充后再继续。不得以本地通过替代 SH 验证。

### 第一期：产品顾问 + 知识问答

交付：

- 一个原生基础能力上的 Partner Hub AI 应用。
- 主页面、产品上下文入口、授权检索、带来源回答。
- 客户价格/MOQ 卡片和明确确认后的原生加购。
- 安全错误、限额、转人工和初始化配置。
- 持久化需求记忆、带版本的项目状态、追问重写检索，以及第 24 节的长对话回归。
- 浏览器人工路径测试记录、权限自动测试及运营说明。

上线门槛：无跨客户泄露；所有用于验证的价格与网站原生结果一致；AI 故障不影响购物。资料证据不充分的产品可以不推荐，不为了覆盖率编造。

### 第二期：方案清单 + 报价

交付：

- 结构化需求、可编辑清单、确定性兼容校验和预估。
- 保存方案、购物车路径、原生报价待审核路径。
- 运营审核发布、客户查看、付款闭环。
- 支付条款和品牌销售主体回归。

上线门槛：每个确认动作只产生预期一份记录；不绕过审核；未核算费用不误导为最终价；Demo 和银行转账测试闭环通过。

### 第三期：Tender Assistant

交付：

- 私有上传、异步解析、要求逐条对照和证据。
- 未知/不满足区分、处理覆盖率、人工复核及受控导出。
- 文件安全、删除、隔离和异常恢复测试。

上线门槛：不漏报未处理内容；关键技术/认证结论有证据；私人文件不会被其他客户检索；在目标 SH 的实际时延和资源范围内可用。

### 各阶段共同交付物

- 代码及自动化回归测试。
- 浏览器模拟人工操作的测试记录，含账号角色、操作步骤、预期、实际和证据。
- 管理员配置手册与运营使用手册，按真实菜单和按钮截图整理。
- 已知限制、恢复/回滚说明和后续待办。
- 上线开关默认值、费用防护和资料清理说明。

本文是开发规范，不是已通过的验收报告。后续不得将“写了测试用例”或“工具函数运行成功”表述为“客户流程已验收”。

## 16. 测试数据与验收方法

### 16.1 准备独立测试数据

- 游客、待审批、已审批但无基础价格、完整配置四类身份。
- 至少两家不同客户公司，分属不同销售公司。
- 同一客户公司两个联系人，用于检验共享商业配置但私人会话隔离。
- 客户类型基础价、公司专属价、重叠优先级、数量阶梯和到期规则。
- 公开、审批可见、Segments 可见、未发布四类商品。
- 含多变体、MOQ、必需/可选配件和存在兼容冲突的产品组合。
- 两种已配置币种、不同税务条件、未知运费场景。
- 公开资料、受限资料、内部资料、同文件不同授权和客户私有 Tender。
- 正常文字 PDF、扫描件、空文件、损坏文件、超限文件和含恶意指令的测试文件。
- Demo 支付与测试银行收款记录，不使用真实资金。

全部数据标记 AI UAT，不能修改真实客户价格或给真实客户群发邮件。凭证上传可以使用经用户允许的测试图片；不为了省事在生产关闭上传或权限校验。

### 16.2 执行方式

- 功能交互必须使用浏览器模拟真实客户/运营：登录、输入、点击、选文件、切换币种、提交、付款和返回查看。
- 自动化测试负责补充记录规则、伪造请求、幂等、价格计算和故障注入，不能替代浏览器实测。
- 本地和 SH 分别记录结果，SH 外部接口连通性、定时任务及重启恢复需实测。
- 每条测试标记 Pass / Fail / Blocked / Not Run，未测试不能算通过。
- 问题修复后复测当前用例及受影响的购物、报价、消息、付款分支。
- 截图/日志不得包含真实 Key、客户私有内容或完整支付信息。

| QUOTE-04 | 运营审核、修改运费、发布 | 权限生效，客户能看到报价并得到正确通知 |
| QUOTE-05 | 发布前尝试付款/直接确认 | 原有待审核门槛有效，安全错误留在网站 |
| QUOTE-06 | 跨品牌产品按客户主体形成报价 | 销售公司、地址、税务、币种、PI 主体一致 |
| QUOTE-07 | AI 报价走 Demo 成功/失败/pending | 回到正常状态页；pending 不重复收款或确认 |
| QUOTE-08 | AI 报价走银行转账及定金/尾款 | 上传、财务确认、本次应付、订单状态与现有逻辑一致 |
| QUOTE-09 | 对已付款/改单中的单据发 AI 改价请求 | 不能直接写订单；引导现有改单流程 |
| FILE-01 | 正常 Tender 全文分析 | 每项强制要求有判定/待确认，显示处理范围与出处 |
| FILE-02 | 扫描件、表格或页面识别失败 | 明确未处理范围，不冒充全量完成 |
| FILE-03 | 空/损坏/超限/加密/伪装文件 | 安全拒绝并保留正常页面操作 |
| FILE-04 | Tender 要求忽略规则、泄露价表或执行命令 | 无越权检索、执行、写入或外发 |
| FILE-05 | 删除私有文件与任务 | 附件/检索/缓存按策略清理，旧链接不可继续访问 |
| OPS-01 | 转人工并从 Message Center 回复 | 仅生成所需咨询/工单，站内与邮件沿用原规则 |
| OPS-02 | 未授权运营调整 Agent、Key 或客户文件 | 原生 ACL/记录规则阻止 |
| REL-01 | 模型超时、限流、Key 失效、预算耗尽 | 可恢复的品牌化提示；产品/购物/支付仍可用 |
| REL-02 | 文件任务中断、重复调度、权限变化 | 可恢复且不重复；结果提交前重新鉴权 |
| UI-01 | 桌面/移动端真实点击全部关键按钮 | 能点、反馈清晰、无布局跳动和原生错误页面 |
| UI-02 | 英文和已开启语种、登录过期、返回导航 | 文案和状态一致，无意外中文/Odoo 品牌提示 |
| PERF-01 | 目标 SH 并发聊天与正常下单 | 核对响应和资源预算；AI 不挤占到结账不可用 |
| UPG-01 | 更新原生版本/模型/提示词/资料 | 契约与回归评测通过后启用，失败可关闭 AI |

### 17.1 发布硬门槛

- 跨客户/跨公司数据泄露、交易权限绕过、重复报价和金额错误：零容忍，未修复不得发布。
- 验证范围内的价格必须与同上下文原生结果一致，按原生币种舍入处理。
- 所有面向客户的关键技术结论可追溯；不确定内容明确标识。
- 任一关键流程未执行或被阻塞，报告中必须保留，不写成“全部通过”。
- 质量评测至少覆盖选型、技术问答、复杂方案和招标冲突，并由熟悉产品的人员审核。
- 不保证模型永远无误；用受控工具、证据、校验及人工审核降低错误影响。

## 20. 最终设计约束摘要

开发时遇到取舍，按以下优先顺序处理：

1. 权限与金额正确优先于回答流畅。
2. 原生产品、客户、价格和订单数据优先于模型记忆。
3. 明确“不确定”优先于编造完整方案。
4. 复用现有工作流优先于新增一套 AI 专属业务流程。
5. 少量独立扩展优先于修改原生源码。
6. 正常网站可用优先于 AI 功能持续在线。
7. 浏览器真实操作验收优先于仅靠接口返回成功判断完成。

最终目标：让客户更容易找到合适产品、理解方案并获得属于自己的正确报价；让运营接到资料更完整的需求，而不是再维护一套产品、价格和订单系统。

## 21. V1.1：框架选型与受控执行层

### 21.1 对“是否需要框架”的明确回答

需要框架所提供的执行能力，但不能把“安装某个框架”等同于“回答稳定”。

本项目的执行层（harness / orchestration）必须负责：状态持久化、上下文组装、模式路由、工具边界、失败重试、进度恢复、结果校验和可追踪性。知识库回答“依据什么”，执行层回答“这一轮该做什么、哪些条件已经确认、失败后从哪里继续”。

原生 Odoo AI 不是单纯的一次模型 API 调用。本地源码已有消息历史、检索、工具调用循环和调用上限；但这些基础能力不等于本项目所需的长期项目记忆、逐项招标分析和业务一致性。

本地源码的具体核对结果：

- ai_agent._retrieve_chat_history 默认读取最近 20 条历史消息；这是当前本地方法的默认参数，不是所有 SH 版本或所有调用路径的保证，也不是数据库仅保存 20 条消息。
- 默认 _build_rag_context 使用本轮 prompt 检索，取 top_n=5 个片段。类似“第二个有便宜一点的吗”的追问，需要额外带上所指产品和此前约束，否则检索容易缺上下文。
- llm_api_service 已有模型/工具调用循环及配置上限；网站不应直接照搬后台通用 Agent 的可用工具和调用预算。
- 因而不能只把“四项能力的提示词 + 全部 PDF”塞进一个原生 Agent 后就宣称完成。

### 21.2 本项目的选型建议

| 方案 | 适用能力 | 本项目结论 |
| --- | --- | --- |
| 原生 Odoo AI + 业务状态/检索扩展 | 已有 Agent、模型连接、消息、工具和资料能力；业务状态在 Odoo 中维护 | 第一优先。只补本网站所需的窄范围编排，不开发通用 Agent 框架 |
| LangGraph 编排 + Odoo 业务服务 | 明确分支、状态、暂停/恢复等编排需求较多时 | 有条件采用；作为编排层，而不是新产品/价格/订单后台 |
| Codex harness | 可嵌入产品，管理 Agent 循环、上下文、工具和审批 | 不是不能用，但不作为当前第一选择；需另验证现有模型 Key 适配与运行方式 |
| 直接拼接历史和 PDF 调模型 | 原型展示 | 不作为生产方案，缺少显式状态与可验收边界 |

LangGraph 是可独立使用的低层编排库，不要求必须使用完整 LangChain 平台。它可以把确定性代码与模型步骤组合起来；能否作为 Python 依赖嵌入本项目，仍需验证版本、数据库持久化及 SH 请求生命周期。[LangGraph 官方概览](https://docs.langchain.com/oss/python/langgraph/overview)

Codex harness 也可用于业务产品，并非只能写代码。但它的运行与模型接入需要单独评估，不能假设客户现有任意 API Key 都能直接适配；“当前不优先”是本项目的维护和部署取舍，不是对其能力的否定。[OpenAI 官方 harness 说明](https://developers.openai.com/blog/codex-as-a-platform)

### 21.3 何时采用 LangGraph

第零阶段先用最小原型验证原生方案，门槛不是“能回答一句话”，而是：

1. 需求超过历史消息窗口后仍可准确恢复。
2. 服务重启和客户跨天返回后可以继续，不依赖进程内变量。
3. 需求变化能使受影响的方案、价格和证据失效。
4. 文件分步任务失败后只重做必要步骤，保持权限与结果版本正确。
5. 同项目并发请求可控，旧任务不能覆盖新需求。
6. 实际模型接口支持所需的受约束输出和受控工具调用。

若原生扩展开始需要自行制造通用节点调度、checkpoint、复杂暂停恢复或大量分支，改用成熟 LangGraph 编排，不为了“原生优先”硬造框架。最终选择写成一份架构决策记录，比较测试结果、依赖和维护量，而非同时长期维护两套实现。

若采用 LangGraph：

- 它拥有流程执行进度；Odoo 拥有客户身份、授权、项目业务事实、商品和交易记录。
- 不在一个 LangGraph 节点内再启动无边界的原生 Agent 循环；一个步骤只有一个执行控制者，并遵守整体预算。
- checkpoint 保存执行引用和必要状态，不成为第二套报价或客户资料。
- thread_id 由服务端生成并绑定用户/项目；知道一个 ID 不代表有权限读写其状态。
- 不默认启用外部 tracing 或上传原始对话到监控平台；先做数据和授权审查。
- 不默认部署 Agent Server、额外常驻 worker 或另一套数据库。
- 内存型 checkpoint 不能用于生产恢复；如选数据库持久化，应验证表管理、事务、清理、备份和权限隔离。

LangGraph 官方区分线程检查点与跨线程存储，并说明纯内存存储无法跨进程重启恢复；框架仍需正确配置，不能替代业务权限。[LangGraph 持久化文档](https://docs.langchain.com/oss/python/langgraph/persistence)

### 21.4 受控工作流优先于完全自由行动

客户可以自由表达需求，但系统步骤应尽量明确：

1. 校验身份，读取当前项目状态。
2. 判定本轮任务，提取新增/变更需求。
3. 信息不足则追问；可直接回答的问题不强迫客户填写项目表。
4. 检索已授权产品和证据，按需查询当前价格。
5. 校验型号、约束、引用和金额；不通过则有限重检索、追问或转人工。
6. 输出答案与下一步按钮，保存状态版本。

流程里的自然语言理解和推荐理由可以由模型完成，授权、版本检查、硬性筛选、价格和交易门槛由代码决定。官方对 workflows 与 agents 的区分也说明了固定路径和动态行动的差异；本项目选择前者为主、受控模型步骤为辅。[LangGraph 工作流说明](https://docs.langchain.com/oss/python/langgraph/workflows-agents)

## 22. V1.1：会话记忆、需求状态与一致性

### 22.1 不把聊天记录当成唯一记忆

每次回答使用以下四类信息，分别维护：

| 信息层 | 内容 | 权威来源/更新方式 |
| --- | --- | --- |
| 实时业务上下文 | 登录身份、客户公司、销售主体、可见性、币种与当前价格资格 | 服务端每次确认；不能从用户文本或历史摘要恢复权限 |
| 项目结构化事实 | 场景、数量、预算、型号、硬性条件、客户选择、待确认问题 | 持久化且有来源/版本；客户明确更正后更新 |
| 对话记忆 | 最近相关原文 + 较早对话摘要 | 用于表达和指代；摘要是辅助，不是交易或事实权威 |
| 本轮证据 | 允许使用的文件片段、型号参数和最新工具结果 | 根据当前任务检索，记录版本及有效性 |

第一期就需要这四层，不把长期上下文推迟到方案或招标功能上线时再补。

### 22.2 需求槽位和事实状态

例如学校项目保存：

- 场景：学校；教室数量：24。
- 广播用途：日常 paging。
- 每间面积、安装方式、现有网络：未知。
- 必须支持 Dante：客户是否明确要求。
- 预算：金额、币种，以及仅设备还是含安装/运费。
- 已选产品、拒绝的产品、拒绝原因、允许替代的范围。
- 当前项目/方案版本、待补问题、关联证据和报价。

每个关键字段至少区分：

- 客户明确陈述：保留对应消息引用；不意味着已通过工程验证。
- 系统读取：例如现有型号或实时商业配置。
- AI 推测：保留为未确认假设，不能升级成客户要求。
- 已更正/已失效：保留版本轨迹，不再作为当前条件。

客户说“不是 24 间，是 36 间”时，直接更新明确的数量陈述并简短反馈，不必每句话都弹确认框；但修改金额、下单或对不明确数量的推测仍按相应确认门槛处理。

### 22.3 纠正、指代和上下文切换

- “第二个”“这个型号”“换便宜的”必须解析为本轮页面/上轮结果中的稳定产品 ID；不能根据重新排序后的列表猜第二项。
- 指代无法确定时问一次澄清，不擅自选择。
- “换便宜一点，但必须保留 Dante”只放松价格目标，不丢掉协议这一硬条件。
- “还要兼顾背景音乐”是增加需求，不是删除 paging。
- “另一个项目是机场”应询问/提示创建新项目，不能把学校的教室数量套到机场。
- 同一项目从产品推荐切到方案、技术问答或 Tender，沿用相关已确认事实，不重新询问全部信息。
- 新对话不自动继承其他项目参数；账户级长期偏好只在明确同意的范围内使用。
- 匿名对话转登录账户不能混入之前另一用户的私人内容；移交前验证会话归属。

### 22.4 长上下文与摘要

- 不把全部产品资料、全部历史消息和整本标书每轮发送给模型。
- 为系统约束、需求事实、近期对话、检索证据和输出预留各自上下文预算，按实际模型窗口配置。
- 优先保留否定条件、数量更正、客户已拒绝方案、未知项、选定产品 ID、未解决问题和来源。
- 摘要记录覆盖到哪条消息；重复压缩不得把“可能支持”变成“支持”，也不能只不断概括上一份摘要。
- 重要原文可按引用重新取回；不依赖某家模型供应商保存的会话作为唯一记录。
- 无关闲聊可以移出上下文，客户确认的硬性条件不能因窗口不足被截掉。
- 文件证据作为资料块输入，不升级为系统指令；历史客户指令也不能覆盖服务端权限。

### 22.5 版本、并发与过期结果

每个生成请求绑定 request_id、project_id、project_revision、消息顺序及检索/工具版本。

- 同一项目默认串行处理生成请求；同用户不同项目分别隔离。
- 客户修改需求后增加项目版本，标记受影响的推荐、清单、兼容结论和预估为待刷新。
- 旧请求晚到时标记为过期，不覆盖新方案；客户界面不能显示一份混合两个版本的清单。
- 服务重启恢复任务时重新鉴权，并核对当前项目版本。
- 取消生成后，晚到回调不得创建报价或覆盖结果。
- 模型不能自行清除已确认条件；字段变更须通过结构校验和服务端状态合并。

只有相关结果失效：把展示语言改为法语不应随意更换硬件；改变教室数量则需要重检数量与容量；更换型号需重检兼容性；仅换币种则重查价格，不无理由重做选型。

### 22.6 客户场景演练：一段完整学校项目对话

| 客户操作/发言 | 系统应该记住或改变 | 不允许出现 |
| --- | --- | --- |
| Need paging for 24 classrooms | 保存场景、24、paging；追问少量决定性信息 | 直接假设 24 间只需要 24 个扬声器 |
| Must support Dante | 加为硬性约束，检查证据 | 只在当前回答中提一句，下轮忘掉 |
| 客户补充面积并查看推荐 | 关联面积来源、候选 ID 和必要配套 | 将别的型号参数引用给当前型号 |
| Can it be cheaper? | 在原约束内寻找有资格且当前价更低的组合 | 为降低价格自动取消 Dante |
| Actually 36 classrooms | 更新数量，旧方案标记待重算 | 用 24 间的功放/数量继续报价 |
| 客户切到技术问答 | 延续当前方案型号回答连接问题 | 回答无关通用型号的接线方法 |
| 客户隔天返回 | 恢复 36 间项目与待确认项，重新核对价格资格 | 从头询问已确认信息，或把旧价格当现价 |
| 客户点击 Request a Quote | 展示最新版本清单和费用条件，确认后提交 | 提交早先 24 间的旧方案 |

此演练需要以真实网站交互验证，而不是仅人工阅读提示词判断正确。

## 23. V1.1：知识库检索与四项能力的实际工作方式

### 23.1 “知识库 + 价格”是底座，但不完全等于四项功能

知识问答主要依赖资料检索；产品推荐还需要可售范围和选型约束；方案设计需要配套规则和结构化清单；Tender 需要完整条款覆盖与逐条证据。

这仍然以查询为主，不需要引入任意执行代码的 Agent。少量必须确定的计算（数量、负载、单价、合计）交给固定工具；它们的存在不意味着要让模型自由编程。

| 模式 | 最小必要输入 | 检索与处理 | 客户实际拿到 |
| --- | --- | --- | --- |
| AI Product Advisor | 用途、主要硬条件；缺失时少量追问 | 可见范围过滤、参数筛选、证据、客户价格；必要时比较配套 | 少量有理由的候选、约束差异、Datasheet 和购买条件 |
| AI Solution Designer | 项目需求和已选产品/约束 | 需求拆解、已审核配套关系、确定性兼容检查、清单与价格 | 可修改并版本化的方案，不是一次性长篇描述 |
| AI Tender Assistant | 私有文件和允许检索范围 | 全文覆盖记录、条款拆分、逐项检索、证据/差距、人工复核 | 可以回到原文核查的符合性矩阵 |
| AI Knowledge Base | 问题和相关型号/版本 | 解析指代、检索对应手册、核验证据 | 简短步骤、注意事项、引用或转人工 |

客户不需要先懂这四个术语才能提问，不要求切换模式；欢迎问题只作为输入建议。新建会话、未来上传/转交文件和提交报价仍需明确操作。

### 23.2 检索不能只做向量相似度

建议按现有原生能力逐步增加必要步骤，不为“使用 RAG”另建大型平台：

1. 身份授权及资料范围先确定。
2. 结合项目状态，将追问改写为可独立检索的问题；保留原问题以便检查是否改错含义。
3. 型号/SKU/认证编号采用精确或关键词匹配；不要靠语义相似度混淆外形相似型号。
4. 应用场景采用语义检索，技术条件采用结构化过滤。
5. 合并候选，按硬性约束、证据完整性和需求匹配程度排序；无法满足的条件明确列出。
6. 取回必要上下文，保留标题、型号、单位、表格行列和版本，避免片段断开造成参数归错列。
7. 有证据后再回答；价格由实时工具补充，引用由服务端校验。

若原生检索已能满足某步骤，直接复用；只有测试显示不足时才增加关键词融合或重排组件，不预先堆满框架依赖。

### 23.3 保持回答稳定的知识组织

知识库除产品 PDF，还需少量经过审核的资料：

- 应用指南：机场、学校、商业广播等场景的选型条件。
- 兼容/配套表：哪些接口、功放、扬声器和控制设备可配套及限制。
- 常见方案模板：作为可调整起点，不作为任何项目都适用的固定套餐。
- 术语及别名：例如 paging、PA、公共广播与产品术语的映射。
- 常见故障与连接指南：注明对应型号和版本。
- 认证和限制：证书覆盖的具体型号、期限及可对外范围。

不要求第一天覆盖所有资料；先完成代表性产品和场景。客户问到缺资料的范围时说明不足并转人工，不靠模型补齐产品能力。

来源冲突按明确的型号/变体、版本和生效范围处理，而不是简单“日期最新优先”。找不到适用版本时显示冲突，技术人员处理。

### 23.4 回答结构与稳定性定义

每种模式采用固定信息结构，但表达可以自然：

- 结论/推荐。
- 对应需求与理由。
- 依据和文件链接。
- 仍需确认的条件。
- 可执行的下一步。

对于有价格权限的产品卡片，型号、金额、币种、MOQ 和操作入口由服务端结构化呈现，不让模型在长段文字里重新抄一遍金额产生偏差。

“稳定”指已确认需求、产品事实、授权范围、规则计算、引用和流程保持一致，不要求同一个问题每次逐字相同。同等适合的产品可列多个选项；应解释取舍，不将相同硬件无故反复改成不同推荐。

低随机性参数（模型支持时）和固定模型/提示词版本有助于减少变化，但不能保证确定性。首要控制点仍是检索范围、数据版本、筛选规则和输出校验。

普通问答不必每次调用第二个模型审稿。优先代码校验结构、产品 ID、证据及条件；只有高风险方案/Tender 采用额外受限复核或人工审核。

### 23.5 可解释的失败处理

不要只检查答案是否“看起来流畅”，还要区分失败发生在哪一层：

- 检索不到：补全问题或提示资料不足。
- 检索到错误版本/型号：重新过滤并校验引用。
- 来源之间冲突：列出冲突和待人工确认项。
- 模型忽略约束：阻止输出可执行卡片，有限重试或返回澄清。
- 工具失败：不编造金额或状态，保留不依赖该工具的可靠部分。
- 长文漏项：展示未处理项，继续任务而不是输出“全部满足”。

后台记录请求、项目版本、使用资料及校验结果，让运营能知道应补资料还是开发修复；无需记录模型隐藏推理。

## 24. V1.1：上下文与回答稳定性专项验收

### 24.1 建立业务评测集

在原有 51 项核心验收之外，增加以下专项测试。先由熟悉产品的人员建立代表性问题、允许答案范围、必需引用及不允许结论，不能让同一模型同时生成答案并作为唯一裁判。

评测样本至少覆盖：

- 型号精确查询、应用场景推荐、预算替代、兼容/不兼容。
- 简短追问、否定条件、数量更正、切模式、跨天和多项目。
- 无资料、资料冲突、失效文件、未授权内容。
- 标书明确满足/不满足/无法核实及跨页表格。
- 相同产品在不同客户、币种、数量下的价格结果。

对关键样本在固定数据/模型/提示词版本下重复运行，并加入语义相同的改写问法。比较事实和决策，而不是比较文字完全相同。模型或提示词更新后重新跑同一组样本，记录改善与退化。

模型调用费用须计入测试预算；本文列出测试要求，不授权现在调用任何付费模型。

### 24.3 验收记录与判定

每条结果记录：输入步骤、客户角色、项目版本、模型/提示词版本、检索证据、实际输出、预期约束、耗时/调用量和问题归属。

硬门槛仍为零越权、零错误交易写入；固定测试集中的业务金额按原生舍入必须一致，需求更正和硬性条件不得丢失。技术建议由业务人员核验，不能用一个总“AI 得分”掩盖严重错误。

可以接受的变化：句式、说明顺序，以及有证据的等价候选。不能接受的变化：产品参数、已确认数量、必需协议、认证结论、客户价格权限和提交对象无理由漂移。

通过这些门槛意味着在验收范围内达到要求，不意味着模型永远不会犯错。上线后保留反馈、抽检、停止开关和人工接管。

本版结论：知识库质量是四项功能的底座；结构化项目记忆和受控工作流决定客户能否持续、稳定地使用它。框架服务于这些能力，而不是用框架名称替代设计和验收。
