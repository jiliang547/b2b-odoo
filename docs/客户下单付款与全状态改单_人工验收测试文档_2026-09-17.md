# Partner Hub 客户下单、付款与全状态改单人工验收测试文档

版本：2026-09-17
代码基线：02499fc，分支 agent/figma-b2b-redesign
适用环境：本地 8070 或 Odoo.sh 独立测试分支
文档状态：测试设计完成；下列用例均为待执行，不代表已经通过。

## 1. 目的和执行边界

覆盖客户从商品页、购物车、结账、付款、订单查看到申请改单的全过程，同时覆盖运营审批、修改方案、财务收款/退款、PI 下载、异常恢复和权限隔离。付款渠道包括 Demo 在线支付与银行转账；付款条件包括 A 全额预付、B 定金加尾款（20/80 和 30/70）、C 发货前全款、D 账期及 E 特殊条款。

本测试必须通过浏览器模拟人工点击、输入、选择文件、保存、刷新、退出和重新登录执行。不得用数据库改状态、后台脚本创建付款、直接调用接口代替客户点击，也不得把自动化单元测试结果填写为人工测试通过。日志与只读技术检查仅用于定位失败原因。

客户、运营、财务分别用独立浏览器配置或独立登录会话。不能全部用管理员账号测试。每条用例结束都从客户页面和后台页面交叉核对。需要按钮却找不到时，先记录 URL、账号角色、公司和截图，不得自行跳过该步骤。

所有付款均为测试交易。银行流水在测试库中模拟登记，不真实向银行付款；Demo 不验证 PayPal 的真实资金清算。邮件只检查测试邮件记录或测试邮箱，不能向真实客户批量发信。外部 ERP 尚未接通时，不宣称完成生产、库存和物流闭环。

## 2. 记录和通过标准

每条用例独立填写：

| 字段 | 记录内容 |
|---|---|
| 用例编号/执行日期 | 例如 PAY-01，日期时间 |
| 环境/提交版本 | URL、数据库、Git 提交 |
| 客户/运营/财务 | 登录名、实际角色、允许访问公司 |
| 业务记录 | 原订单号、改单号、修订报价号、付款号、凭证号、PI 版本 |
| 前置状态 | 总额、净收款、余额、付款比例、交付量、发票状态 |
| 实际步骤 | 与文档不一致的按钮名称或路径也要记录 |
| 实际结果 | 状态、金额、提示原文、客户是否可继续操作 |
| 证据 | 客户前后截图、后台截图、PDF、相关时间点 |
| 结论 | 待执行 / 通过 / 失败 / 阻塞 / 不适用 |
| 缺陷关联 | BUG 编号、复测结果 |

通过：界面操作成功且金额、状态、权限、记录数量全部符合预期。
失败：可重复出现与预期不一致的业务或界面行为。
阻塞：前置数据、权限或外部集成缺失；必须写明原因，不能记通过。
不适用：明确属于未启用的另一履约模式；列出范围和依据。

每条异常用例都要验证：提示后业务数据没有部分更新，没有重复收付款或重复改单，返回后仍能继续正常操作。前台应保留品牌页面并显示可理解的英文提示；不得出现原生 Oops、技术堆栈、Odoo 品牌弹窗或无限等待。

## 3. 账号、公司和测试资料

### 3.1 测试账号

| 账号代号 | 要求 |
|---|---|
| C-A | 已审批，属于客户公司 A，绑定销售公司 A 和品牌 A |
| C-A2 | 同客户公司 A 的另一联系人，用于公司共享范围验证 |
| C-B | 属于独立客户公司 B，绑定销售公司 B |
| C-PENDING | 已激活但未审批 |
| C-NOPRICE | 已审批，客户类型尚未配置有效基础价格 |
| OP | 普通 B2B Operator，无 Manager、财务或管理员角色 |
| MGR | B2B Manager，有对应销售公司及销售业务访问权 |
| FIN | B2B Finance，具备原生收付款所需会计权限；执行 Finance Complete 的账号还需对应原生会计权限 |
| ADMIN | 仅用于初始化，不代替 OP/MGR/FIN 验证 |

运行跨公司测试时，MGR/FIN 勾选销售公司 A、B；当前公司先设 B，再操作 A 客户订单，随后交换。不要把“右上角勾选全部”当成权限授予。

### 3.2 前置配置检查

1. 后台 B2B Management → Business Setup：确认销售公司、网站、品牌、履约模式。
2. B2B Management → Operations → Brand Receiving Accounts：确认各品牌关联合法销售公司与该公司银行日记账。
3. Accounting → Configuration → Journals：打开对应 Bank 日记账，核对公司、币种、银行账户持有人、收款方式和付款方式的未结清科目。
4. 各销售公司已经安装会计科目表；测试客户在该公司下具有有效应收科目；银行日记账代码在公司内唯一。
5. B2B Management → Configuration → Customer Types & Base Pricing：确认客户类型、网站、币种基础价格以及公司专属覆盖。
6. B2B Management → Business Data → Customers：打开客户公司 Partner Hub，配置品牌、审批、分类及 Collection Terms。
7. 在测试环境启用 Demo 支付并确认客户的销售公司/币种能够使用。记录实际付款界面提供的成功、失败等选项；没有某种模拟选项就记环境限制。
8. 商品 P1 单价 USD 100，MOQ 1；P2 单价 USD 50；另准备 MOQ 10 的商品、隐藏商品和不可售商品。以实际订单明细税费为准，基准用例总额固定 USD 1,000。
9. 基准订单不含税及运费；其他用例单独增加运费或税。不要为测试修改真实商品税务配置。
10. 配置 A、B20、B30、C、D，以及 E：生产前 40%、发货前 100%。D 配置充足信用额，并另备逾期/超限客户。
11. 银行账户补充资料使用英文；Notes 已用于对外 PI，不得填内部密码或内部备注。

## 4. 入口与通用人工步骤

### 4.1 客户下单（流程 S）

1. 用客户账号登录，进入 Products。
2. 点击商品详情，选择变体，输入数量，点击 Add；观察提示与购物车数量。
3. 打开购物车，检查商品、SKU、数量、单价、小计、币种。
4. 点击结账，选择/填写收货及账单地址，进入支付页。
5. 核对总额，然后根据用例选择 Pay Now、Submit Order 或 Pay by Bank。
6. 保存订单号，在 My → Orders & Payments 中分别查看 Orders、Quotations，打开详情与 Payments & PI。
7. 刷新并退出重新登录，核对订单仍存在且金额一致。

### 4.2 Demo 支付（流程 D）

1. 从结账页或订单详情 Accept & Pay 进入实际支付窗口。
2. 选择 Demo，核对付款金额和币种，点击 Pay。
3. 如显示模拟状态选项，选择本用例要求的状态；成功主流程选择成功。
4. 等待跳回订单页，不能手动把交易改成完成来代替此步骤。
5. 客户检查付款摘要；FIN 在原生 Payment Transactions 中按订单/引用查看交易状态、金额及关联订单。
6. 核对收款只计一次；刷新、返回、重复打开回执不产生第二笔。

### 4.3 先提交报价再付款（流程 R）

1. 客户按 S 点击 Submit Order。
2. MGR：B2B Management → Operations → Orders Pending Review，搜索订单号并打开。
3. 在原生订单明细修改数量、商品、单价或新增运费行；使用表单顶部保存图标保存。重新打开确认已保存。
4. 填写必要客户说明；核对总额、公司和币种。
5. 点击 Release for Customer Payment。
6. 客户刷新订单详情，查看最终金额，再用流程 D 或 B 支付。
7. 未释放前，客户不应可以支付旧金额；不能只通过改文案判通过。

### 4.4 银行收款（流程 B）

1. 客户按 S 点击 Pay by Bank，进入 Payments & PI，下载当前 PI。
2. 查看应付金额和银行账户；上传测试凭证，填写本次转账金额、日期、银行引用，点击页面上传表单提交按钮。
3. 客户应看到待财务审核。此时净收款不得增加，也不得仅凭截图释放生产/发货。
4. FIN：B2B Management → Operations → Bank Transfer Reviews，搜索订单号并打开凭证。
5. 点击 Register / Open Receipt，进入原生收款。核对客户、公司、银行日记账、币种、日期和实际到账金额。
6. 保存并点击原生 Confirm；必要时打开会计分录核对已过账和科目完整。
7. 返回原凭证审核单，核对关联的 Payment；填写 Allocated Amount，表示本笔实际收款分配给该订单的金额。
8. 点击 Confirm Actual Receipt，在确认弹窗确认。
9. 客户刷新，核对净收款、余额、当前应付及订单归类；FIN 核对未新建第二笔付款。
10. 分次付款每次重复上述操作，保存每次收款编号。不能把“客户申报金额”当成实际到账金额。

### 4.5 已确认订单改单（流程 C）

1. 客户从订单详情点击 Request Change，填写修改理由和具体商品/数量/费用，提交。
2. MGR：B2B Management → Operations → Order Changes，按原订单号搜索并打开申请。
3. 核对原订单及履约情况，点击 Start Review。
4. 点击 Edit Proposed Order，在弹出的修订订单中修改明细。
5. 点击弹窗底部 Save & Close；返回申请，重新打开修订确认修改已保存。不是点击原订单 Confirm。
6. 点击 Send to Customer。
7. 客户刷新原订单，进入 View Change Requests 或 Order Changes，打开该申请。
8. 客户逐行对照方案、原金额、新金额、差额，点击 Accept Revised Order 或 Decline Proposal。
9. 按用例处理补款或退款。原订单号应保持不变，修订订单只作为方案记录，不应被当成第二张可独立付款的客户订单。
10. 客户接受前原订单明细不得提前被替换；接受后可能已经应用新明细并进入补款/财务审核，不应误要求一律等补款后才更新明细。

### 4.6 退款与财务完成（流程 F）

银行退款：FIN 从申请提供的 Register / Open Bank Refund 入口进入；若页面未提供，记录情况，再通过 Accounting 的客户付款入口创建该客户的原生付款（方向 Send/Outbound）。核对销售公司、客户、银行日记账、币种和实际退款金额，保存并 Confirm，核对已过账。返回改单申请，在 Bank Refund Payment 关联该笔付款。

Demo 退款：FIN 打开该订单原 Demo 交易，使用原生退款操作，核对退款成功并关联原交易；回到改单申请 Finance 页，在 Refund Transaction 选择该退款。若 Demo 未提供退款操作，记阻塞，不能用一条自由输入参考号冒充已退款。

两者择一关联，填写 Finance Reference；有已过账发票时，先按原生流程处理贷项通知单/补充发票并核对关联，再点击 Finance Complete。刷新客户页面，核对净收款、余额、退款结果及通知。不得直接删除原付款/发票来“修正”历史。

## 5. 金额判断与状态基准

当前应付款按收款条件、已确认收款和改单状态判断，不能直接把订单差额当成本次应付款。

| 条件 | 订单 USD 1,000、已收 0 时 | 满足条件后 |
|---|---|---|
| A | 生产前收 1,000 | 已确认；未有交付证据时不得称已发货 |
| B20 | 先收 200 | 进入 Orders，余额 800；发货前需累计 1,000 |
| B30 | 先收 300 | 进入 Orders，余额 700；发货前需累计 1,000 |
| C | 允许先确认/安排生产 | 发货前仍需累计 1,000 |
| D | 信用校验通过可确认 | 按原生发票到期日收款，不等同已付款 |
| E 40/100 | 先收 400 | 余额 600，发货前累计 1,000 |

页面 Orders 与 Quotations 的依据是订单确认状态，不是是否付清全部货款。Deposit Received · Balance Outstanding 与 Fully Paid 是付款摘要；Order Confirmed 不是物流状态。

收款方案中的生产/发货比例，与原生 Payment Terms 的发票到期日是两套用途。测试应同时核对，不能把原生 30 天账期自动解释成允许无定金生产。

## 6. 正常下单及支付主流程

各行均使用新订单。步骤中的 S/D/R/B/C/F 对应第 4 节完整点击流程。

| ID | 人工操作 | 预期 |
|---|---|---|
| PAY-01 | C-A，A 条款，S→D 成功付 1,000 | 订单确认、净收 1,000、余额 0；无二次扣款 |
| PAY-02 | C-A，B20，S→D 付 200；MGR 在订单 Collections & PI 点击 Request Balance Payment；客户 D 付 800 | 定金后进入 Orders；尾款前不可认定可发货，尾款后 Fully Paid |
| PAY-03 | C-A，B30，S→D 付 300，再付 700 | 每阶段金额正确，原订单付款累计 1,000 |
| PAY-04 | C-A，A，S→B 付 1,000 | 待审核不计款，财务确认后确认订单 |
| PAY-05 | B20，S→B 先收 100，再收 100，最后 800 | 100 时不达定金；累计 200 才确认；累计 1,000 才满足付款放行 |
| PAY-06 | B30，S→B 先 300 后 700 | 定金、尾款通知、凭证历史正确 |
| PAY-07 | C 条款，S→银行提交，暂不付款，再 B 收 1,000 | 无款可确认，不应显示已付款或已发货 |
| PAY-08 | D 条款，信用充足，S→银行/约定条款提交；财务创建原生发票再登记收款 | 无款确认符合授信；发票到期日正确，收款后余额减少 |
| PAY-09 | E 40/100，B 收 399、1、600 | 399 不达标，400 达标，尾款门槛正确 |
| PAY-10 | A，S→R，MGR 加运费 100，客户 D 付 1,100 | 客户先看最终报价；旧 1,000 不能直接支付 |
| PAY-11 | A，S→R，MGR 减商品后总额 900，客户 B 收 900 | 以释放后的金额付款，原订单保留 |
| PAY-12 | B20，S→R，加运费至 1,100，再 D 付 220、B 收 880 | 定金基数包含最终费用；混合渠道不重复计款 |
| PAY-13 | B30，先 B 收 300，再 D 付 700 | 银行与在线合计 1,000，关联客户/公司一致 |
| PAY-14 | C-B 重做 PAY-01、PAY-04 | 销售公司 B、品牌 B、银行 B、PI 抬头和财务归属正确 |
| PAY-15 | 五家销售公司各建一单，分别付款 | 各公司金额/账簿隔离；同一财务可处理获授权公司 |
| PAY-16 | 从首页商品卡、Products 卡片、商品详情分别 Add 后下单 | 加购反馈、数量、变体与价格一致，按钮不变形 |
| PAY-17 | 运费/税/折扣商品组合下单，再付款 | 购物车、支付窗口、订单、PI 总额一致，金额以真实配置计算 |
| PAY-18 | 改用另一支持币种重做 PAY-04 | 页面、银行、PI 和财务币种正确；不把非 USD 当 USD |

## 7. 付款前及支付异常

| ID | 人工操作 | 预期 |
|---|---|---|
| EX-01 | 访客进入结账/订单链接 | 正确登录引导；无他人数据 |
| EX-02 | C-PENDING 登录并尝试下单 | 不能绕过审批看到受限价格或提交订单；品牌页面说明原因 |
| EX-03 | C-NOPRICE 登录、商品页、购物车 | 价格配置提示；无原生错误页、错误零元订单 |
| EX-04 | MOQ 10 商品输入 1、9、10 | 前两者被提示/合理校正，10 可下单 |
| EX-05 | 数量为空、0、负数、小数、过大 | 单位及业务限制有效，无负金额或崩溃 |
| EX-06 | 隐藏/下架商品旧链接及旧购物车继续结账 | 重新验证可售性和可见性 |
| EX-07 | 空购物车点结账；提交后浏览器返回再提交 | 不生成空单/重复订单 |
| EX-08 | Demo 选择失败，再重试成功 | 失败不计款；可以恢复完成付款 |
| EX-09 | Demo 选择取消或关闭窗口，再回订单 | 订单未误标已付款；可继续支付 |
| EX-10 | Demo pending/authorized（若可模拟） | 不按实际到账计算；没有该模拟入口记阻塞 |
| EX-11 | 付款回跳慢时刷新、双击 Pay、双标签页付款 | 不重复收款；结果最终一致；异常应可恢复 |
| EX-12 | 提交银行订单/Submit Order 双击及浏览器后退重提 | 无重复订单，购物车重置正常 |
| EX-13 | 支付页面停留期间 MGR 修改报价 | 客户只能确认最新金额或收到刷新提示，不能支付失效报价 |
| EX-14 | 待审核报价尝试旧支付链接和 PI 下载 | 不绕过报价释放限制 |
| EX-15 | MGR 待审核时改数量、加/删商品和运费，保存后重开 | 修改持久化；释放后客户收到新金额 |
| EX-16 | MGR 拒绝/取消待审核订单，客户打开旧页付款 | 已取消订单不能继续支付或上传凭证 |
| EX-17 | 缺品牌银行、银行币种不匹配、销售公司未启用 | 显示明确配置提示；不展示其他公司的银行 |

## 13. 履约边界

当前主要是外部 ERP 履约。银行到账、订单确认和付款条件放行只代表资金/订单状态，不代表工厂生产或仓库出货。

外部模式必须记录以下未接入验收项：生产确认后改单限制、ERP 接受/拒绝改单、重复通知幂等、部分发货和全部发货同步、付款冲销后的履约拦截。未提供接口及测试数据时全部记“阻塞—ERP 尚未接入”，不得用测试人员口头确认代替系统闭环。

若测试环境另外启用 Odoo 原生工厂模式，用独立订单执行：生产确认→运营确认工厂允许变更→修订供货单→客户接受→补退费用→库存交货。不能为了完成此项切换已有真实订单的履约模式。

## 14. 执行顺序与退出条件

1. 完成前置账号/公司/会计/Demo 检查，保存配置截图。
2. 先跑 PAY-01、PAY-04、PAY-10、PAY-11，证明两种付款和报价释放均可闭环。
3. 跑 A/B/C/D/E 和五公司主流程。
4. 跑 ST 状态入口、CH 金额矩阵、CE 改单异常。
5. 跑 BANK、EX 异常；每次制造异常后补跑一次相应正常流程。
6. 跑 UI，实际打开 PI PDF 检查。
7. 缺陷修复后用原操作复测，并回归该分支的正常流程。
8. 输出总表：通过/失败/阻塞/不适用数量、未解决 BUG、ERP 等待项及实测订单索引。

任一重复扣款、跨公司/跨客户泄漏、错误退款、付款被虚计、已交付订单被覆盖都属于阻止上线的问题。功能测试中途遇到缺陷，可以继续不依赖该缺陷的用例，但不能最后省略失败项。
